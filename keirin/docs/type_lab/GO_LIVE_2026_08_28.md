## 1. 売るもの

1レースの型がプランをちょうど1つ決める（`src.type_lab.sell_plans_for`）。
**型は排他なので 1レース1商品が構造的に守られる**——優先順位の設計が要らない。

| 型 | プラン | 券種 | 点数の目安 |
|---|---|---|--:|
| A 鉄板 | `A_hit` | 三連単 | 3〜5 |
| B 堅い・中 | `B_hit` | 三連単 | 3.5 |
| C 崩れ筋 | `C_hit` | 三連単 | 12 |
| D 混戦・軸あり | `D_hit` | 三連複 | 4 |
| E 混戦・中 | `E_hit` | 三連単 | 14 |
| F 大混戦 | `F_pay` | 三連単 | 4 |

`rank_key` は **プラン名そのもの**（`A_hit` … `F_pay`）。`type_lab_picks.plan_key`
と同じ値なので、入稿と検証台が結合キーなしで突き合わせられる。

## 3. ゲート

| ゲート | 掛かるもの | 実測の落ち方（確認窓） |
|---|---|---|
| 軸信頼（プラン内 下位1/5） | **看板レース以外** | 全体の 21.0% |
| 平均想定払戻 > 20,000円 | 全部（看板も） | `A_hit` の 16%・`D_hit` の 3%。他は無傷 |
| 1点の予測オッズ >= 2.0倍 | 全部（看板も） | **0件**（ダッチ配分＋帯で構造的に満たす） |

🔴 **看板レースは軸信頼ゲートを素通しする。** ゲートを素で当てると看板の **26%**
（3.78件/日・899/3,460件）が消える。売上の 84% が看板に集まるので、
「看板レースには必ず推奨を出す」（2026-08-09 のユーザー方針）を優先した。
⚠️ 代償は、落ちる側の層（表示的中 18.74%・ROI 68.7%）が看板に混ざること。
   §2 の 22.0%/78.7% は**看板を含めた値ではない**（含めると 20.16%/77.5%）。
⚠️ 素通しは**軸信頼ゲートだけ**。平均払戻と1点オッズは看板にも掛ける
   （ユーザーが明示的に決めた入稿方針で、看板へ広げるかは別途の判断が要る）。

## 3.5 🔴 別ランクが取ったレースには出さない

netkeirin は **1レース1商品**。型ラボの `rank_key` は既存ランクと別物なので、
ループの `(race_key, plan) in already` では**既存が取ったレースを止められない**
（そのまま出すと netkeirin 上で既存の商品を上書きする）。
`races_taken_by_other_ranks()` が `_already_submitted()` の戻り値から
「型ラボ以外のランクが取ったレース」を導いて弾く。

全面置換後は既存が全部 OFF なので普段は空だが、**移行期・ロールバック中・
看板穴埋めが動いた日**に効く。実測（2026-08-28 の dry-run・既存が稼働中）では
65レース中 **22レース**がこれで落ちた。

⚠️ `_already_submitted()` は**ランクを絞らず全ランクの行を返す**。初版はそれに
   気づかず専用クエリから `already` の race_key を差し引いており、**常に空集合**
   ＝ガードが一度も効かなかった（dry-run の内訳を数えて発覚）。

## 3.6 「自信あり」（1日1レース）

ユーザー決定（2026-08-28）:
**「20,000円以上の払い戻しになりそうで、最も的中率が高そうなレース」**。

    候補 … `type_lab_picks.pred_min_payout >= 20,000`
           （＝**どの目が当たっても** 2万円以上。「平均」では約束にならない）
    順位 … Σp（`legs[].prob` の合計＝その商品の的中確率）が最大

🔴 **旧経路のままだと壊れる。** `race_expected_value` は**三連複の買い目しか
   対象にしない**（`bet_type != "3連複"` を全て None にする）。型ラボ6プランの
   三連複は `D_hit` だけなので、放置すると「自信あり」が **D_hit にしか付かない**。

🔴 **呼ぶ場所を移した。** `daily_picks_wt.sh`（07:00）は型ラボの生成・入稿（07:15）
   より**前**に走るので、そこで呼んでも当日の型ラボの行を1件も見られない。
   `type_lab_daily.sh` の**入稿の直後**へ移した（承認時に `is_confident` が読まれる）。

実測（`pred_min_payout >= 20,000` かつ Σp 最大を毎日1件）:

| | 探索2025 | 確認2026 |
|---|---|---|
| 選定できた日 | **365/365日** | **238/238日** |
| 表示的中 | **28.8%** | **34.9%**（全体は 20.16%） |
| 払戻中央 | 27,450円 | 27,880円 |
| プラン内訳 | C_hit 166 / D_hit 114 / B_hit 45 / E_hit 38 / A_hit 2 | C_hit 97 / D_hit 92 / B_hit 29 / E_hit 20 |

Σp が実績と対応することも両窓で確認した（五分位の表示的中: 探索 7.26 → 25.56% /
確認 6.33 → 27.06%）。

🔴 **Σp は較正されていない。** PL 由来の確率は過信側に出る
（[[keirin_7m1_ev_gate_rejected_2026_08_25]]: 本番PL 0.271 → 実測 0.151）。
実測でも探索窓は Σp中央 0.375 ↔ 実績 29.6% と過信（確認窓は 0.369 ↔ 35.3% で一致）。
**絶対値は信じず、1つしかない枠をどこへ置くかの相対比較にだけ使う**——既存 EV と同じ扱い。
⚠️ 記録先の列名は `confident_ev` のままだが、型ラボのときの中身は **Σp**。
   尺度が違うので**日をまたいで比べない**。

⚠️ **穴狙いアイコンは承認経路では付かない。** `approve_and_submit` は
   `RANK_CONFIGS[rank_key]["act_type"]` を見るが、型ラボの rank_key はそこに無い
   （＝既定 or 自信あり）。既存の入稿スクリプトを1行も変えない方針とのトレードオフで、
   承認制 ON（現行）では `netkeirin_submit_type_lab.ACT_TYPE_BY_PLAN` は使われない。

## 5. 手順

### 5.1 デプロイ前（コードを入れる前）

```sql
-- 🔴 型ラボの6ランクを **enabled=false で先に INSERT する**。
--    `_is_enabled()` は fail-open（行が無いと常時ON）なので、
--    これを忘れるとデプロイした瞬間に入稿が始まる。
INSERT INTO keirin.netkeirin_settings (rank_key, enabled)
VALUES ('A_hit', false), ('B_hit', false), ('C_hit', false),
       ('D_hit', false), ('E_hit', false), ('F_pay', false)
ON CONFLICT (rank_key) DO NOTHING;
```

### 5.2 デプロイ

`main` へマージ → VPS へ配備 → `type_lab_daily.sh` / `type_lab_wave.sh` を cron へ。

```cron
# 型ラボ（本番入稿・2026-08-29〜）
20 7 * * *   $KEIRIN_HOME/scripts/type_lab_daily.sh >> $KEIRIN_HOME/data/logs/cron.log 2>&1
0 13 * * *   $KEIRIN_HOME/scripts/type_lab_wave.sh noon    >> $KEIRIN_HOME/data/logs/cron.log 2>&1
0 18 * * *   $KEIRIN_HOME/scripts/type_lab_wave.sh evening >> $KEIRIN_HOME/data/logs/cron.log 2>&1
# 採点（従来どおり・上流 intraday_results_wt.sh の刻みに合わせる）
5,20,35,50 8-23,0 * * *  $KEIRIN_HOME/scripts/type_lab_settle.sh >> $KEIRIN_HOME/data/logs/cron.log 2>&1
```

🔴 **`type_lab_daily.sh` は「組む → 入稿する」を1本の中で行う。** 以前は入稿
（07:00 の `daily_picks_wt.sh`）が型ラボの生成（07:15）より**先**に走っていた。
既存の入稿経路へ相乗りさせていたら、当日の行がまだ無い状態で入稿が走り
**毎朝0件のまま誰も気づかない**ところだった。

### 5.3 切り替え（デプロイ後・稼働の直前）

```sql
-- 既存ランクを全部止める
UPDATE keirin.netkeirin_settings SET enabled = false
 WHERE rank_key IN ('7H2','7T1','7T3','7S','7B','7C','7H1','7M1','7A','7SS',
                    '9H1','9C','9A','9S','9SS','S1');
-- 型ラボを開ける
UPDATE keirin.netkeirin_settings SET enabled = true
 WHERE rank_key IN ('A_hit','B_hit','C_hit','D_hit','E_hit','F_pay');
```

## 9. 測って否定したもの（再提案しないこと）

**型Fを条件で `F_hit` / `F_pay` へ振り分ける案**（2026-08-28・ユーザー提案の検証）。
軸1と軸2の乖離 `d = (P(1着=軸1) − P(1着=軸2)) / (P(1着=軸1) + P(1着=軸2))` で
半分ずつに振り分け、**同数を無作為に振り分けた対照20本**と比べた
（再現: `scripts/exp_type_lab/typef_split_control.py`）:

| 母集団 | 全F_hit | 全F_pay | 無作為中央 | 乖離大→hit | 乖離大→pay |
|---|--:|--:|--:|--:|--:|
| 7車 探索2025 (5,765R) | 25.64% / 73.7% | 9.12% / 66.1% | 17.37% / 70.0% | 17.05% (**2/20**) | 17.71% (18/20) |
| 7車 確認2026 (2,934R) | 25.19% / 79.4% | 8.52% / 65.5% | 17.02% / 74.3% | 15.85% (**1/20**) | 17.86% (20/20) |
| 9車 全期間 (2,025R) | 16.94% / 69.2% | 6.07% / 60.5% | 11.70% / 65.2% | 11.01% (**2/20**) | 12.00% (18/20) |

- 🔴 **「乖離が大きいほど F_hit」は3母集団すべてで無作為対照に負ける。**
  実際は逆で、`F_pay` の表示的中は乖離が**大きい**ほど上がる
  （探索 7.72→10.23% / 確認 6.31→10.17% / 9車 2.96→9.14%・いずれも単調）。
  軸1が抜けているほど「1着＝軸1固定」が効く、という素直な方向。
- 🔴 **向きを逆にしても採用に値しない。** 無作為には勝つが ROI の向きが窓で
  一致せず（8/20・19/20・12/20）、得られるものが両端に届かない——表示的中は
  全F_hit の 25.2% が最大、10万+ は全F_pay の 65件が最大で、
  **分割は中間（17.9% / 32件）を作るだけ**。
- 機序は `SUMMARY.md` §2.6「型は edge を作らない。決めるのは帯とカバレッジだけ」と同じ。

🔴 **件数や構成を入れ替える検証には必ず無作為対照を置くこと。**
「半分を `F_hit` に替える」だけで表示的中は必ず上がるので、対照が無いと
どんな分割規則でも「効いた」ように見える（`race_filter_2026_08_27.md` と同型）。

## 10. まだ測っていないこと

1. **売上（pt/R）**。想定平均払戻 3〜4万円の三連単には前例が無い（`SUMMARY.md` §3）。
   全面置換なので比較対象が残らない。**1週間は日次で売上を見ること**
2. **9車の `F_pay`（決勝限定）は 67件中 表示的中2件**＝収支は判定できない。
   件数は 1.05件/日 なので全体への影響は小さい（9車全体で 87.2% → 85.4%）
3. **軸信頼ゲートそのものが「採用」ではない**。確認窓を判断に使っており
   （一度きりを消費）、向きが両窓一致するのは 6プラン中 5。
   **前向きの実地で確かめる段階**であることは移行後も変わらない
