# レースの選定と適用プランの切り替え条件の見直し（2026-10-17）

ユーザー依頼（2026-10-17）:

> レースの選定、レースに適用するモデル条件が適切になることで的中率、回収率の向上ができないか検証して。
> 適用モデルの切り替え条件の見直しになると思います

結論を先に4行:

1. **明確に勝てる切り替え規則は無かった。** 試した規則はどれも「表示的中を上げると払戻（4万+・10万+）が下がる」
   という同じ交換の上にあり、回収率の差は両窓そろって 0 を跨ぐ。探索窓で選んだセル別の最良プランは
   **確認窓で回収率 −4.8pt**（CI が 0 の下）と崩れた。
2. **現行の切り替え（型→プラン）と残し方（`cap_priority`）は無作為より良い。** プランを無作為に入れ替えると
   回収率が 3〜6pt 落ち、残すレースを無作為に選ぶと現行が表示的中で 20/20・回収率で 19/20・15/20 勝つ。
   今の仕組みは仕事をしている。
3. **残った候補は1つ（効果は小さい）**: 「混戦 ∧ `arare`=1 のレース（いまは型F）を型E として扱い `E_hit` で売る」。
   回収率 **+1.6 / +1.8pt**（探索 CI [+0.1, +3.0] / 確認 [−0.6, +4.0]）・表示的中 +0.6 / +0.9pt（両窓 CI>0）・
   4万+ +0.06 / +0.04件/日。半期に割っても4区間と端数35日のいずれもプラス（+0.6〜+2.5pt。
   端数の 2026-07-01〜08-04 は +8.2 だが35日しか無い。いずれも同じ2窓の分割で、独立の証拠ではない）。
   代わりに看板枠 `F_sign` が1日約1件減り、10万+ が −0.02 / −0.04件/日。
4. 候補は両窓を見て選んだ腕なので**事前登録が要る**。判定は比較台を 2026-08-05 以降へ延ばして行う（§6）。

判定基準は [[feedback-roi-pass-criteria]]（現状比 → 最低合格75% → 理想100%）。
数値は 探索 2024-07〜2025-12（549日）/ 確認 2026-01〜08-04（216日）。

### 4.2 さらに分けると — 看板枠の置き換えが半分

混戦 ∧ `arare`=1 で現行が売るのは `F_hit`（1.5件/日）と `F_sign`（準決勝系・決勝系、約1件/日）。
`F_hit` だけを `E_hit` に替えると ΔROI +0.4 / +0.9・Δ表示 −0.4 / −0.2（`a6_fe.py`）で、
「払戻を上げて的中を下げる」いつもの交換に近い。**表示的中も回収率も上がる部分は `F_sign` → `E_hit` の側**にある。

🔴 ただし `F_sign` の回収率はそもそも台で測れていない（上位10件除外で 30〜65% へ落ちる・
[[keirin-outlier-robustness-2026-10-13]]）。「看板枠をやめると回収率が上がる」は方向だけで、
量は信用できない。売上面では看板枠は1本あたりの売上が大きい（`bet_review` H15）ので、
**表示的中・回収率の小幅改善と、看板（10万+）の減少との交換**として判断が要る。

## 6. 事前登録の案（判定は未見の期間で）

- **変更**: `race_shape` の列の境界を混戦側だけ `arare >= 2` → F（`arare`=1 の混戦を E）にする。
  堅い側（C/B）は変えない
- **判定期間**: 2026-08-05〜2026-12-31（比較台の終端 2026-08-04 より後＝今回まだ見ていない期間）。
  🔴 **2026-08-05〜10-17 の分を先に覗かないこと**（ここが事前登録の対象そのもの）
- **判定の台をどう作るか（未整備）**:
  - 比較台は `exp_tf20/build_board.py` → … → `build_race_type_board.py` で作るが、元になる
    vintage walk-forward 予測 `data/exp_cache/wf_preds_*.pkl` は **2026-08-04 で終わっている**
    （最終ファイル `wf_preds_2026-07-16_2026-08-04_f60_2024-04-01.pkl`）。台を延ばすには
    同じ手順で 2026-08-05 以降の vintage 予測を作り直す必要がある
  - 🔴 本番の前向き記録（`type_lab_picks` の `live`）は**そのレースの型のプランしか組まない**ので、
    型F のレースに `E_hit` の行が無く、そのままでは使えない。代案は生成側（`build_type_lab_picks.py`）に
    「型F ∧ `arare`=1 のレースへ `E_hit` の紙上の行を足す」変更（売らない・コード変更なので別 PR）
  - どちらで行くかはユーザー判断。前者は過去分も作れる・後者は今日からしか貯まらない
- **主指標**: 日次上限ありの全商品で ΔROI >= 0（点推定）∧ Δ表示的中 >= 0
- **副指標**: 上位3件除外の ΔROI >= 0・Δ10万+/日 >= −0.05
- **検出力**: 動く行は約2.5件/日（`F_hit` 1.5 + `F_sign` 1.0）×約150日 ≒ 375件。
  主指標は「点推定が 0 以上」なので、**本当は効果が無くても約1/4 の確率で通る**
  （ΔROI と Δ表示的中がそれぞれ半々で正になる場合）。通っても「否定されなかった」程度の強さで、
  採用は副指標と合わせて判断する
- 主指標を満たせば本番の変更（`type_label_of` と `race_shape` の列境界・`test_type_lab_submit.py` の固定値）を提案する。
  ΔROI < −1.0pt なら閉じる
- 混戦の下位（`axis_sum` < 1.327）は `L_flat`（`flat_lead_2026_10_02.md`）が別に前向き判定中で、
  対象が一部重なる。両方が採用になる場合は `L_flat` を先に当て、残りに本案を当てる
