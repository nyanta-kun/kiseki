### 1.1 🔴 A-1: 採点が同着を落としていた（最重要）

2026-08-22 に `src/result_top3.py`（同着の当たり目を作る唯一の正本）を新設し、既存ランクの
`backfill_7*_rank_wt.py` は全部そちらへ移したが、**型ラボの採点だけが移されていなかった**。

`_finish()` が `{着順: 車番}` の辞書で持っていたため:

- **3着同着** → 後勝ちで片方が消える。しかも SQL に `ORDER BY` が無く**非決定的**
- **1着/2着同着** → 1・2・3 がそろわず**永久に未採点**

**例外もログも出ない。**

実例 2025-10-27 岸和田6R（1着=1番 / 2着=4番 / **3着=2番と6番の同着**）:

    A_hit  買い目 1-4-5 / 1-4-3 / 1-4-2(1,800円)   → 記録 hit=False payout=0
    A_pay  買い目に 1-4-2 と 1-4-6                  → 記録 hit=True  payout=221,910

**同じレース・同じ台帳の中で片方のプランだけが的中を落としていた。**

さらに、確定オッズは目ごとに別々に公表される（実測 `1-4-2 = 28.0倍` / `1-4-6 = 170.7倍`
が**両方とも板にある**）ので、2目とも買っていれば**両方とも当たり**:

    A_pay の正しい払戻 = 1,800×28.0 + 1,300×170.7 = 272,310円

`result_top3.hit_trifecta` / `hit_trio` は**1つしか返さない**。あちらは他ランクが共有する
正本なので **API は変えず**、型ラボの採点側で全当たり目を舐めて合計するようにした。

🔴 **同じ取りこぼしが既存ランクにもありうる**（`backfill_7*_rank_wt.py` は `hit_trifecta` の

## 4. 🔴 未決（商品定義に触るので直していない）

### 4.1 `B_hit` が「賭け金 0 円の買い目」を常態的に含む

`prob_top` は Σ(1/予測オッズ) が上限を超える候補を `break` せず **`continue`** するため、
Σ枠が埋まったあとも「1/o がごく小さい＝極端に高いオッズ」の点を拾い続ける。
ダッチ配分ではその点の取り分が 1 単位（100円）に満たず **0 円**になる。

| | |
|---|---|
| 0円の点を含む行 | **3,052行**（全部 `B_hit`。B_hit 4,947行の **61.7%**） |
| `pred_min_payout` の中央値（B_hit） | **0 円**（他プランは 2〜5.7万円） |
| `pred_mean_payout` の中央値（B_hit） | **26,461円**（設計の「想定平均払戻 3万円の床」を下回る） |

実例 `20250101_22_09`: 6点目が `1-6-3` **0円** / 予測 4,742倍 / prob 0.0001。
**影響**: 表示点数が実際に買う点数と違う / 画面の「想定最低」が0円 / プラン定義の床を満たさない /
その点が当たると `hit=true, payout=0` になる（実績0件だが構造上起きうる）。

**`break` にするか `allocate` で1単位未満を落とすかで商品が変わるので、実測してから決めること。**

### 4.2 `AXIS_SUM_FIRM = 1.44` は 7C と「同じ値」だが「同じ量」ではない

7C は `_gate_p3_sum`（**較正後**の `p3_sum_top2_cal`）を 1.44 と比べる。
`keirin_p3_calibration.py` の docstring は「壊れるのは **p3 の絶対値を見るゲート
（7C の 1.44 / 9C の 1.30）**」と、まさにこの用途のために作られたと書いている。
型ラボは `lgbm_wt_eval` の**生の p3** を同じ 1.44 と比べており、較正を通していない。

    決勝    raw 1.450 → cal 1.416（堅い → 混戦）  ずれ −0.034
    準決勝  raw 1.450 → cal 1.437                 ずれ −0.013
    予選/一般 raw 1.450 → cal 1.440               ずれ −0.010

＝ **決勝・上位グレードが不当に「堅い」側（A/B/C）へ寄る**。
境界帯の母集団は 決勝 1,503件中 **85件(5.7%)**、全体 **991件(2.8%)**。

**バグと断ずるより設計判断の確認事項。** ただしコメントの「7C と同じ定数を使う」は
事実と違うので直した（値は同じ・量が違う）。テストで値の drift は止めた。

## 7. 🟢 見たが問題なし

- `_proportional` は合計を必ず守る — 実測 **58,901行すべてで legs の賭け金合計 = budget**、
  `n_legs` = 実際の点数も全行一致、負の賭け金 0件
- `conf` の床が予算に収まらないときは `None` を返す（黙って薄めない）
- 払戻の端数 `int(round(stake*odds))` は正本 `keirin_settlement.payout_per_100` と
  **12,118的中すべてで差 0**
- 採点の「当たっているのに確定オッズが引けない → 保留」「外れは配当を待たない」の切り分け
- `window()` の型使い分け（DATE ↔ VARCHAR ↔ race_key 先頭8桁）、`venues` を絞り込み前に作る、
  ゲートを競合判定より前に掛ける、`live9` を3エンドポイントで受ける
- `type_lab_daily.sh` の前日+当日採点・9車失敗が採点を巻き添えにしないガード・`mode='live9'` の付与
- テーブル制約 `UNIQUE(race_key, plan_key, mode)`（重複行は構造的に発生しない）
