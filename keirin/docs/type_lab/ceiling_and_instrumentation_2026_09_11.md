## 問い1-1: 「この程度の不振は何日おきに必ず起きるのか」

### 実測: 板（paper・7プラン・765日・27,719行 → 当てにいく行23,719行）

全期間の基準線: **表示的中 27.36%**（n=23,719・1日あたり平均31.0件・最小11〜最大54件）。

N日移動窓（重複あり・非重複ブロックでも同じ値。ロバストネス確認済み）で
「基準線から Xpt 以上低い」が来る頻度:

| 窓 | 基準−3pt | 基準−5pt | 基準−7pt | 基準−10pt | 基準−15pt |
|---|--:|--:|--:|--:|--:|
| **1日** | 36.6%（月11.1回・週2.6回） | 27.7%（月8.4回） | 19.6%（月6.0回） | **12.0%（月3.7回・週0.8回）** | 2.4%（月0.7回） |
| **3日** | 27.8%（月2.8回） | 15.3%（月1.5回） | 6.4%（月0.65回） | 1.4%（月0.15回≈7ヶ月に1回） | 0件 |
| **5日** | 21.6%（月1.3回） | 7.1%（月0.4回） | 0.8%（月0.05回） | 0件 | 0件 |
| **7日** | 15.9%（月0.7回） | 2.4%（月0.10回） | 0.4%（月0.02回） | 0件 | 0件 |
| **14日** | 6.0%（月0.13回≈8ヶ月に1回） | 0件 | 0件 | 0件 | 0件 |

（「月○回」は N日窓の観測比率 × 30.4/N。窓は重複させて数えているが、
非重複3日/7日ブロックで同じ表を作っても 27.8%/15.6% など**ほぼ同じ値**になることを確認済み
——重複による過大推定ではない。）

### 実入稿（14日）での裏取り

同じ「基準線−Xpt」を実入稿（当てにいく8プラン・14日・634件・基準線29.02%）で見ると:

    2026-08-29 -6.80  08-30 -4.53  08-31 -6.07  09-01 +10.51  09-02 -11.78
    09-03 +4.98  09-04 -0.45  09-05 -4.95  09-06 +7.82  09-07 +14.73
    09-08 +0.52  09-09 +1.17  **09-10 -10.15**  09-11 +8.76

**14日中2日（09-02・09-10）が「−10pt以下」＝14.3%。** 板の推定（12.0%）とほぼ一致する。
＝**板の頻度分布は実入稿の短い履歴とも整合する**ので、頻度の答えとして使ってよい。

3日移動窓（12窓）では最悪が **09-08〜09-10 の −3.02pt**（09-09〜09-11 は最終的に **−0.55pt**
まで戻る）。**板の分布で「3日窓が−3pt以下」は27.8%（月2.8回）＝ごく普通**。
recent_drop.md が「3日連続」として扱っていたものは、この表で見れば
**もともと『月に何度も来る』水準にすら届いていなかった**、というのが実測の言い方になる。

### 読み方

🔴 **09-10 単日の −10.15pt は「月3〜4回・週0.8回」来る通常の日。** ユーザーの言う
「運の分」はここで量として書ける：**単日で見れば10pt級の下振れは珍しくない**。
🟢 **3日窓・7日窓・14日窓まで束ねると急速に稀になる**（3日−10pt は月0.15回・7ヶ月に1回級、
7日−5pt はほぼ来ない）。つまり **「連続して悪い」と言うためには最低でも1週間分の
窓で測るべきで、2〜3日分の印象では判定できない。**

## 問い1-2: 表示的中 ↔ 10万+/日 の交換レート（1本の曲線）

`daily_portfolio_2026_09_10.md` §5（確認窓・確定値）を並べ直す:

| 役割 | 件/日 | 表示的中% | 10万+/日 | 単位あたり10万+率 |
|---|--:|--:|--:|--:|
| 当てにいく（`_hit`/`_trio`） | 16.66 | 30.46 | 0.023 | 0.00138/件 |
| 配当狙い（`A_ana`/`F_pay`） | 1.09 | 4.26 | 0.032 | 0.02936/件 |
| 看板（`F_sign`） | 3.50 | 4.76 | 0.120 | 0.03429/件 |
| 高額枠（`{B,C,D}_sign`/`_big`） | 4.44 | 3.55 | 0.148 | 0.03333/件 |

当てにいく1件を一撃系1件に**置き換える**（総件数25.69件/日は固定）ときの増減:

| 置換先 | Δ表示的中/件 | Δ10万+/日/件 | 傾き(Δhp÷\|Δ表示的中pt\|) |
|---|--:|--:|--:|
| 配当狙い | −1.02pt | +0.0280 | 0.0274 |
| 看板 | −1.00pt | +0.0329 | 0.0329 |
| 高額枠 | −1.05pt | +0.0320 | 0.0305 |

**3つの一撃系はほぼ同じ傾き（0.027〜0.033）に乗る。** ＝ どの一撃枠を使っても

    10万+/日 ≈ 0.030 × （諦める表示的中のpt）

という**1本の直線**で書ける。月換算では **「表示的中 1pt を諦めるごとに 10万+ が
月に約0.9件（≈33日に1件）増える」**。逆に言えば、**表示的中を1pt上げたければ
10万+ を月1件弱失う**、というのがDESIGN.md 2.1の主張の定量版。

⚠️ **これは「現在の運用点まわりの局所的な傾き」**。実際に動かせる範囲は在庫で頭打ちになる：
- 高額枠は**設計5本のうち68%の日が既に満杯**（現在4.44/5本）。増やせるのは残り0.56本/日だけ。
- 看板（`F_sign`）は `SIGNBOARD_RACE_TYPES`（決勝・準決勝系）の開催数で規定され、
  「今日は何レース決勝があるか」という**外生的な量**。触れるノブは`HIGHPAY_SLOTS_PER_DAY`
  （5→N）と`SIGNBOARD_RACE_TYPES`の範囲、`A_ana`の`pw_ent`閾値（1.4076）だけ。
- 大きく振った場合（例: 高額枠を5→20本のような桁の変更）にこの直線が保つかは
  **未測定**（観測点は現在の運用点1つだけ）。

### 仕分け

🔴 **判定不能（実務のスパンで確認できない）**:
- 表示的中の **±1〜2pt の変化**（1〜3年かかる）。`docs/type_lab/` の多くの改善提案が

- **10万+/日 のどんな小さな改善**（+10%程度）も**十年単位**。これは既存の
  「ROIを±2.5ptに収めるのに15.6年」という言い方の**同型の姉妹指標**である。

🟢 **判定可能（数週間〜数ヶ月）**:
- 表示的中の **±5〜10pt の変化**（3〜8週間、実入稿の件数なら1〜2週間）。
  09-10のような単日の下振れ規模（-10pt）は検出力の話にすら乗る大きさ。
- 10万+/日 を **2倍以上動かす変更**（半年〜2年）。ただし現行の一撃系の設計はどれも
  「表示的中を1pt渡して10万+を0.03増やす」程度の**局所的な微調整**しか許さないので、
  実際に2倍化を狙うなら**在庫の頭打ち（高額枠68%満杯・看板の開催数依存）を先に解く**
  必要があり、それ自体が別の設計変更になる。

**結論**: 「的中率が上げきれない」という感覚に対して、**日次〜週次で判断できる指標は無い。**
月次で見て良いのは「表示的中±5pt以上・件数の大きな変化」だけで、それ未満の差は
**問い1-1の分布の中に埋もれる**（09-10がまさにその実例）。

## 問い2: `DESIGN.md` 4.3 の5分類を毎日焼き付ける設計

### 0. 実現可能性の裏付け（先に）

研究用スクリプト `scripts/exp_type_lab/miss_anatomy_build.py` が、**板（frozen vintage）
に対して既にこの5分類に必要な計算を行っている**（`rank_prob` / `both_in3` / `set_hit` 等）。
つまり「できるかどうか」は解決済みで、問題は「**本番の生成・採点パイプラインに
焼き付けていない**」ことだけ。以下はこれを `type_lab_picks` へ移す設計。

実データで1点、重要な罠を確認した（`race_key=20240706_83_03` / `C_hit`）:

    決着 (1,2,4)。軸2車(2,1)は両方3着内＝軸は崩れていない。
    このオーダーの「全210通りの中の確率順位」は **rank_prob=1（全体で最有力）**。
    しかし決着の予測オッズ po_win=4.99倍 < C_hit の帯 min_odds=15.0倍。
    → 帯で切られて候補にすら入っていない。正しい分類は **③帯下決着**。

**「グローバルな確率順位（帯を無視した210通り中の順位）」だけでは③と④を区別できない。**
先に帯（`min_odds`）でふるい、**その中での順位**で④a/④bを分けるという順序が必須。

### 1. 足す列（`keirin.type_lab_picks`）

| 列名 | 型 | 生成/採点 | 何を入れるか | NULL の意味 |
|---|---|---|---|---|
| `plan_axis1` | INTEGER | 生成 | その**プランが実際に軸として使う**1台目の車番。通常は `shape.order[0]`（既存`axis1`と同じ）だが **`F_line`（`structure="line_axis2_flow"`）だけ `shape.line_pair[0]`**（既存`axis1`は常に`shape.order[0]`なので`F_line`では実は違う車を指している——既存の潜在的な不整合） | 軸の概念が無いプラン（`A_ana`＝軸1を除外する側） |
| `plan_axis2` | INTEGER | 生成 | 同上の2台目 | 同上 |
| `plan_min_odds` | NUMERIC(6,2) | 生成 | `plan_used.min_odds`（`build_with_gate_fallback`が返す**実際に使ったPlanバリアント**の値。フォールバックで変わりうるため`PLANS[plan_key].min_odds`をコード側で引き直さない） | 帯を持たないプラン（0扱いでも良いがNULLで「無帯」を明示） |
| `candidate_probs` | JSONB | 生成 | **「軸2台(`plan_axis1`,`plan_axis2`)を両方含む」全ての合法な目**（三連単なら3台の順列すべて・三連複ならframozenset）を、`prob`降順で `[{"combo":"1-2-4","odds":12.3,"prob":0.041}, ...]`。件数は7車で最大30（三連単）/5（三連複）、9車で42/7。帯は掛けない（生成時に決まっていないと後で③と④が判定できないため、ここは無帯の全件を持つ） | 一撃系プラン（`ONESHOT_PLANS`）は分類しないので常にNULL |
| `outcome_class` | VARCHAR(16) | **採点** | `'hit' / 'read_axis' / 'read_band' / 'legs_budget' / 'legs_model'` のいずれか | 未採点・一撃系・`candidate_probs`が空（backfill前の古い行） |

サイズ実測見込み: `candidate_probs` は7車で最大30エントリ×約35バイト(JSON圧縮後)≈1KB。
**軸restrict済みなので当初想定した「210通り全部」より1桁小さい**（②read_axisは
既存の`axis1`/`axis2`だけで判定できるため、候補は「両軸そろっている前提」の
③④判定にしか使わない→軸を含む目だけで十分、というのがこの設計の要点）。

### 2. 生成側のどこで焼き付けるか

`scripts/build_type_lab_picks.py::rows_for_race()`（64〜140行目）の
`built = build_with_gate_fallback(...)` の直後（108行目付近、`gate_mean`計算の後）に追加する。
その時点で `shape`（`RaceShape`）・`plan_used`（採用された`Plan`。フォールバック込み）・
`odds`/`prob`（そのbet_typeの全合法目の辞書。既に変数として存在）が全部スコープにある。

```python
a1p, a2p = (shape.line_pair if plan_used.structure == "line_axis2_flow"
            else (shape.order[0], shape.order[1]))
if plan_used.key in CORE_PLAN_KEYS:            # 一撃系は計算しない
    need = {a1p, a2p}
    cand = sorted(
        ((k, float(odds[k]), float(prob.get(k, 0.0))) for k in odds
         if _pos(odds[k]) and need <= set(k)),
        key=lambda t: -t[2])
    candidate_probs = [{"combo": _combo_str(k, plan_used.bet_type),
                        "odds": round(o, 2), "prob": round(p, 6)}
                       for k, o, p in cand]
else:
    a1p = a2p = None
    candidate_probs = None
```

`CORE_PLAN_KEYS` は既存 `type_lab_design_report.py::CORE_PLANS` と同じ集合
（`A_hit,A_trio,B_hit,C_hit,D_hit,E_hit,F_hit,F_line`）——**2箇所に定義を持たせない**ため、
`type_lab_design_report.py`側から輸入するか、`src/type_lab.py`に定数として1つだけ置く。

`COLS`（441〜443行目）に `plan_axis1 plan_axis2 plan_min_odds candidate_probs` を追加し、
`rows_for_race()`の返り値dict（119〜139行目）に4フィールドを追加する
（`legs=json.dumps(detail, ...)` と同じ書き方で `candidate_probs=json.dumps(candidate_probs, ...) if candidate_probs is not None else None`）。

⚠️ **`n_legs`をそのまま「買った点数」として④a/④bの閾値に使ってよいのは
`UPPER_BANDS=()`（現在オフ）の間だけ**。将来また上帯を投入したら`add_upper_band`が
`legs`を増やすため、④a/④bの閾値には**上帯を重ねる前の点数**を使うこと
（`gate_mean`と同じ箇所で確定する`len(legs)`を、必要なら`n_core_legs`として
別列に焼くのが安全。今回は上帯オフなので優先度は低いが、注意点として明記）。

### 3. 採点側でどう5分類へ落とすか

`scripts/settle_type_lab_picks.py::main()` のループ内（142〜193行目）、
`f = fin.get(t["race_key"])` が取れた直後に追加する。`f`は既に `[(着順,車番),...]`
（3着内が確定した行）を持っているので、`top3 = {fn for _, fn in f}` が使える。

```python
def classify(plan_key, hit, top3, a1p, a2p, decided_combo, cand_json,
             min_odds, n_legs):
    if plan_key not in CORE_PLAN_KEYS:
        return None
    if hit:
        return "hit"
    if a1p is None or a2p is None or cand_json is None:
        return None                              # backfill前の行
    if not ({a1p, a2p} <= top3):
        return "read_axis"
    cand = json.loads(cand_json) if isinstance(cand_json, str) else cand_json
    hit_entry = next((c for c in cand if c["combo"] == decided_combo), None)
    if hit_entry is None or hit_entry["odds"] < float(min_odds or 0.0):
        return "read_band"
    inband = sorted((c for c in cand if c["odds"] >= float(min_odds or 0.0)),
                    key=lambda c: -c["prob"])
    rank = next(i for i, c in enumerate(inband, 1) if c["combo"] == decided_combo)
    return "legs_budget" if rank <= n_legs else "legs_model"
```

`decided_combo`は既存コードが`win`として計算している値（同着時は`representative(wins)`。
既存の代表選択をそのまま使う——同着は0.2〜0.5%しかないので別扱いにする必要はない）。
`UPDATE`文（196〜199行目）に `outcome_class = ?` を追加するだけで済む。

`build_type_lab_picks.py::SETTLE_COLS`（451行目）に`outcome_class`も加える。
これで「買い目(`legs`)が変わったら採点をNULLに戻す」既存の仕組み
（491〜493行目の`clear`）が`outcome_class`にも自動的に効く
（`plan_axis1`等は生成時に毎回上書きされるので`SETTLE_COLS`には入れない）。

### 4. 過去分の backfill は可能か
