## 5-1. 決勝レースの未カバー

### 決勝の定義（正本: `backend/src/services/keirin_marquee.py::is_marquee_race` の一部）
`race_type LIKE '%決勝%' AND race_type NOT LIKE '%準決勝%'`。実データで確認した限り
「ガールズ決勝」「チャレンジ決勝」等は拾い、「準決勝」は除外される（実装どおり）。

⚠️ **n=17は極小でCIも計算できないほど狭い**が、方向としては「軸ゲートが落とした決勝候補は
ゲートを通った決勝候補（表示的中19.15%・下記参照）よりさらに悪い」という一般的なゲートの

### 「看板は必ず出す」方針は型ラボ移行後、明示的に撤回されている
1. **`origin='marquee_fill'`（旧ランク経由の穴埋め・`keirin/scripts/submit_marquee_wt.py`
   `keirin/src/marquee.py::marquee_race_nos`）は 2026-08-28 18:00:22 を最後に0件**
   （`netkeirin_submissions` 実測）。
2. `keirin/scripts/daily_picks_wt.sh` に **2026-08-30 の明示コメント**:
   「従来ランクの入稿と看板穴埋めをここから外した（ユーザー決定『型ラボの入稿を7時の
   実行にし、従来の入稿は無効とする』）」。理由は旧ランクが全て `enabled=false`（08-28）に
   なり、`submit_marquee_wt.py` のフォールバックランク（`RANK_BY_CARS={7:"7S",9:"9C"}`）が
   もはや存在しない商品を呼び続けて全滅していたため（実測 2026-08-30: 埋まらなかった21件）。
   代わりに「穴埋めの役割は型ラボ側へ移した（9車の型Fを売るようにした）」とある。
3. **より根本的に、`backend/src/services/keirin_type_lab_gate.py::_passes_axis_gate`
   のdocstring（2026-08-31）が「看板は必ず出す」方針そのものを取り消したと明記**:
   > 「2026-08-28の『看板は素通し』を取り消した…全体43.2→39.4件/日・表示的中25.96→26.83%・
   > ROI82.4→83.8%（確認2026）…**代償は『看板レースに商品が出ない日がある』こと（3.8件/日）**。
   > 2026-08-09の『看板レースには必ず推奨を出す』方針を、2026-08-31にユーザーが明示的に
   > 取り消した上での変更。戻すなら `_is_marquee(row)` の素通しをここへ復活させるだけでよい。」
   → つまり **軸信頼ゲートは決勝を含む看板レースにも掛かる**設計であり、これは
   「必ず出す」方針の意図的な撤回である。
4. 2026-09-06以降 `origin='highpay_fill'`（軸ゲート/日次上限落ちを高額枠 `{型}_sign/_big` へ
   差し替え）が新設されたが、`highpay_plan_for()`（`keirin/src/type_lab.py:1435`）は
   **型A・E・F・9車を対象外**とする。実測した20件の未カバー決勝は F_sign(型F)・A_hit/A_trio
   (型A)が15/20を占めるため、**この救済策の対象にすらならない**。C_hit(型C, 4件)のみ
   理論上救済されうるが、実測では09-02・09-11のC_hitが軸ゲート落ちのままhighpayにも
   回っていない（同日の高額枠5枠は他の決勝以外のB/C/D落ちに先取りされていた）。

**結論**: kiseki/CLAUDE.md や keirin/src/marquee.py の docstring が語る「看板レースには
必ず推奨を出す」は、**2026-08-31に軸信頼ゲート適用開始・2026-08-30に旧ランク穴埋め全廃
という2つの決定によって、型ラボ移行後は実質的に撤回されている**。現状は「決勝の
83%程度（97/117）に何らかの商品が付く」状態であり、「必ず出す」ではなく「軸信頼ゲートを
通れば出す」に変わっている。これはドキュメント（`keirin/src/marquee.py`のモジュールdocstring
がいまだに「看板レースとその前後には必ず推奨を出す」という2026-08-09方針を主目的として
説明している）と実装の間の食い違いである。

## 5-2. line_swap（並び違い）効果量の食い違い

### 現行コードの line_swap
`keirin/src/type_lab.py`:
- `LINE_SWAP_PLANS = {"B_hit","C_hit","E_hit","F_hit"}`（L1989）
- `LINE_SWAP_LEGS = (2,1)`（L2019）: 確率下位2点、入稿ゲートを割るなら1点
- `LINE_SWAP_MIN_ODDS = 10.0`（L2066）: 差し替え先の予測オッズ下限
- `apply_line_swap()` / `line_legs()`: 先頭×番手の両方向を優先、残りは安い順

### 3つの数字の系譜（git blame で特定）
1. **`keirin/src/type_lab.py` L2003-2008 のコメント「C_hit +2.89 / +3.88」**:
   これは `LINE_SWAP_LEGS` 定数の根拠として書かれた**歴史的な実験記録**（「2点→無理なら
   1点」版・**確定オッズ**で並べ替えを行う `line_legs.py` の再現、`keirin.wt_odds` の
   settled odds を使用）。探索2025/確認2026、7車・33,730レース中の子集合。
2. **doc `keirin/docs/type_lab/line_legs_2026_09_05.md` の最初のコミット
   （`9f64ff41`）には「C_hit +2.79 / +3.74（35/44%）」という別の版の数字があった**
   （`git show 9f64ff41:...line_legs_2026_09_05.md` L136 で確認）。これは「是正後の本番関数
   （10倍下限＋先頭×番手優先）を実データへ当てた再現」の初稿の数値で、**その後の修正コミット
   `9536ac66`（オッズ下限＋先頭×番手両方向の希釈修正PR#470）で `+1.33 / +1.55`（C_hit）へ
   置き換わっている**。現行の `line_legs_2026_09_05.md` には `+2.79/+3.74` は存在しない
   （grep で確認済み・現存するのは §4「2点→無理なら1点」表の `+2.89/+3.88` と §「是正後」の
   `C_hit +1.33/+1.55` の2種）。
3. **メモリ `keirin-handoff-2026-09-11` の「+0.16/+0.26pt・両窓CI 0跨ぎ」** は
   `keirin/docs/type_lab/tau_adaptive_stacked_2026_09_11.md` が出典（同ファイル冒頭の結論表・
   「`apply_line_swap` が `C_hit` にほとんど効いていない…発動率58%もあるのにΔ表示的中は
   +0.16[-0.89,+1.30]/+0.26[-0.32,+0.81]（両窓ともCIが0を跨ぐ）」）。

### 3つが食い違う理由
**測定に使う「オッズの種類」が違う**。
- (1)(2) はいずれも **`keirin.wt_odds` の確定オッズ**で差し替え先の目を選び順序を決めている
  （`line_legs.py` 冒頭コメントに明記: 「並べ替えは確定オッズで行っている（本番は予測オッズ）。
  向きは変わらないが量は前向き実測で確かめること」と自ら警告している）。
- (3) は `/tmp/race_type_board.npz`（vintage walk-forward の **予測オッズ** `odds_tf_n7`）を
  使った `build_with_gate_fallback`（本番と同一の生成関数）による再現で、**本番が実際に
  参照できる情報だけ**を使っている。`tau_adaptive_stacked_2026_09_11.md` はこの差を
  「`LINE_SWAP_LEGS`の節が載せるC_hit +2.89/+3.88pt は確定オッズで並べた別の台の数字で、
  予測オッズで組む本番相当では出ない」と明記している。
- 機序（同docより）: 確定オッズでは「安い目」と「高い目」の区別が正確にできるため
  `LINE_SWAP_MIN_ODDS=10` のフィルタが有効に働き差し替えが多く発動するが、予測オッズは
  ノイズが乗るため C_hit では差し替えられる候補がそもそも薄い（「差し替えが `C_hit` では
  元から薄いから」）。

### 現行の本番配分のもとでの効果（再測定・スポットチェック）
`type_lab_picks`（mode='paper', plan_key='C_hit', n_entries=7, settled済み）の的中率を
自分で集計し、ドキュメントの水準と矛盾しないかを確認した:
```
confirm(2026-01~)        n=2215  的中28.67%  ROI 84.5%
explore(2024-07~2025-12) n=5238  的中28.05%  ROI 77.9%
```
これは `tau_adaptive_stacked_2026_09_11.md` が報告する「本番の全機構込みでの表示的中
+2.99〜+3.65pt」のベースライン水準（的中20%台後半）と整合的で、データが破損していないことを
確認した。ただし **line_swapだけを分離した counterfactual を自分で再構築する時間予算は
無く**、`tau_adaptive_stacked_2026_09_11.md` の実装（本番の`build_with_gate_fallback`を
`--repo`で切り替えて別プロセスで比較・無作為対照20/20）をコード上でトレースし、
手法上の欠陥（例: 前提の`RaceShape.lines`が空で`apply_line_swap`が発動しない旧台の不具合、
`A_line_pos`のfloat/int変換バグ）を本人たちが発見・修正した記録が同docに残っていることを
確認した。**数値そのものの独立再現はできていない**（再現には`/tmp/race_type_board.npz`の
再構築が必要で1回10分超・COMMON.mdの制限に抵触しうる規模）。

### 結論
- **正しいのは (3)（メモリ / `tau_adaptive_stacked_2026_09_11.md`）**。理由は「本番が
  実際に使える情報（予測オッズ）で測っているか」という一点に尽きる。(1)(2)は
  ドキュメント自身が「確定オッズで測っている」ことを明記した上での参考値であり、
  本番効果の見積もりとして使うべきではない。
- (2)のさらに古い版（+2.79/+3.74）は、同一ドキュメント内の**改訂前後の数字が混在して
  残っていた**ことが原因（git履歴で確認）。現行docは修正済みで、+2.79/+3.74は既に
  存在しない。タスクの引用はおそらく改訂前のコミット時点のキャッシュ/記憶によるもの。
- **C_hit個別としてはline_swapはほぼ無効（+0.16/+0.26pt、CI 0跨ぎ）**。ただし
  `apply_line_swap`全体（B_hit/E_hit/F_hitを含む）としては「本番の全機構」から
  外すと-0.37/-0.42pt失う（同docの表）ので、**C_hit以外のプラン（特にE_hit・B_hit・F_hit）
  では効果が残っている可能性が高い**——本タスクではC_hitのみ深掘りしたため、
  他プランの予測オッズベースでの効果は未検証（統括者への提案に記載）。

## 5-3. rule_version の汚染

### 事実確認
- `keirin/src/type_lab.py::rule_version()`（L2736）は `PLANS` と主要定数を JSON 化して
  ハッシュ化する設計だが、**2026-09-11 PR#567（τ適応・並べ替え・押さえ目の3機構追加）
  の時点で `Plan.tau_adaptive` / `Plan.target` / `Plan.bust` / `ORDER_SWAP_PLANS` /
  `OSAE_PLANS` の5つが payload に含まれておらず**、rule_version が変化しなかった
  （`git show e018af84 -s` のコミットメッセージで確認）。
- 影響区間: **2026-09-08 18:06〜（`9619f3cb7668`が始まる波）〜2026-09-14 PR#576適用まで**。
  この間に少なくとも2026-09-11のPR#567適用前後で商品定義（C_hitの点数が12点固定→
  6〜16点可変、B_hit/F_hitの並び順）が変わったが、rule_versionは`9619f3cb7668`のまま
  据え置かれた。
- **2026-09-14に修正**（`e018af84`, PR#576）。修正コミット自身が「9619f3cb7668が
  2026-09-11を境に2つの別商品にまたがる」ことを明記し、「遡っては直せないので、この版で
  絞るときは日付でも切る」と注意書きを残している。

### 実際に汚染された分析の特定
1. `keirin/docs/type_lab/recent_drop_2026_09_11.md`（同日執筆・PR#576適用前）の
   「E. 年表」節は `rule_version` の切り替わりを商品変更の目印として使い、2026-09-11
   09:15（#566 旧ランク除去）以降「変わらず」としているが、**同日のPR#567
   （τ適応等）はこの年表に一切登場しない**（マージ時刻がこの文書執筆後だった可能性が高い）。
   同docは「rule_versionの切替日が低下の開始と一致する」という仮説を自ら実測で否定して
   いるため、**年表の欠落が誤った結論を導いた形跡はない**（＝的中率低下の原因を
   rule_versionの変化に帰属させる誤りは、この文書自身が防いでいる）。
2. `keirin/docs/type_lab/synth_odds_floor_2026_09_14.md`（3節）が明示的にこの汚染を
   発見・記録: 「ブリーフの『rule_versionは9/8以降9619f3cbで固定＝商品は変わっていない』
   は成り立たない」。ここでいう「ブリーフ」は特定できなかったが（ドキュメントファイルとしては
   見つからず、口頭/チャットの要約と思われる）、**この思い込みに基づいて『合成オッズの低下
   原因はC_hitの帯下差込（#508）だけ』と単純化していた可能性がある**。同docは
   date-basedな比較（8/28〜9/8 vs 9/9〜9/13）で再検証し、τ適応（#567）と型C帯20→15倍
   （2026-09-01）も同じ向きに寄与していたと訂正した。**この訂正によって「9/8〜9/11の
   変更は失敗だったか」という最終結論（⑥いいえ、設計通り機能している）は変わっていない**
   ——date-based比較を使っていたため、rule_versionのバグ自体は最終結論には影響していない。
3. `backend/src/api/keirin_type_lab_router.py` は `rule_versions` をレスポンスに含めるが、
   **これは表示用のメタデータ（フィルタ範囲に含まれる版の一覧）であり、統計をrule_version
   単位でグループ化する用途には使っていない**（grep で GROUP BY 等の使用なしを確認）。
   画面集計はdate/mode基準なので、このバグの影響は受けない。
4. `keirin/scripts/exp_type_lab/` 配下・`keirin/scripts/` 配下を横断的にgrepしたが、
   `rule_version` を条件にした母集団分割（`WHERE rule_version = ...` 等）を行っている
   スクリプトは `exp_7m1_add_legs.py`（無関係な旧ランク実験）と `synth_floor_build.py`
   （`cf39e62d1442`という別の・汚染区間外のversionを参照するコメントのみ）の2件のみで、
   いずれも2026-09-08〜09-14の汚染区間とは無関係。

### 結論
- rule_versionの取りこぼしバグは実在し、2026-09-08〜09-14の約6日間、**C_hit/B_hit/F_hitの
  商品定義が2回（#508/#513は含まれる、#567は含まれない）変わったのに版が1つに潰れていた**。
- ただし、**この期間に「rule_versionだけで母集団を分けて結論を出した」分析は見つからず**、
