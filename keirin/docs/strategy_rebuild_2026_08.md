### 1.4 では何が違うのか — 日次回収率への寄与

1レース1万円・1日N件のとき、**1件の的中が日次回収率を押し上げる量は
`倍率 ÷ N`**。N=15 の日で:

| 商品 | 的中時中央倍 | 1件的中の日次寄与 | 日次100%に必要な的中数 |
|---|---|---|---|
| 7C | 1.57 | +10.5pt | **9.6件**（15件中） |
| 7M1 | 5.22 | +34.8pt | 2.9件 |
| 7H1 | 8.38 | +55.9pt | 1.8件 |
| 7T1（目標15万） | 約19倍 | **+127pt** | **1件** |

🔴 **これが構成を変える唯一の理由。** 平均 ROI は構成では動かない（後述）が、
**「1件的中で日次プラス」になるのは払戻が N万円を超える商品だけ**。
ベース層は 15件中10件当てないと日次100%に届かず、的中率 38% では起こりえない。

## 3. 設計原理 — T と N を自己整合させる

1レース1万円固定なら、1件の的中で日次100%を超える条件は:

```
払戻 >= N × 10,000      （N = その日に買う件数）
```

つまり **目標払戻 T と件数 N は `T = N × 10,000` で自己整合**させるべき量で、
片方だけ動かす意味がない。既存の 7T1（三連単・目標15万・1〜2点）は
**N=15 と組んだときに初めて設計として閉じる**。

| N | 自己整合 T | 意味 |
|---|---|---|
| 10 | 10万 | 当たりやすいが一撃が小さい |
| **15** | **15万** | 現行 7T1 の目標額と一致 |
| 20 | 20万 | ユーザー提案の上限 |
| 30 | 30万 | 一撃は大きいが的中頻度が落ちる |

⚠️ **恒等式の上限**: `P(払戻 >= T) <= ROI × 10,000 / T`。ROI 0.8・T=15万なら
1レースあたり **5.3% が理論上限**で、しかもそれは「回収の100%が15万超から来る」
極限。7T1 の実測 3.04% は上限の 57% に達しており、**買い目の形を工夫して
これ以上増やす余地は小さい**。

## 6. どこに伸びしろがあるか（レバーの棚卸し）

### 6.0 恒等式で天井が決まっている

[[keirin_highpay_payout_ceiling_2026_08_06]] の恒等式:

```
P(払戻 >= T) = 帯ROI × 予算 / T          （市場効率下・予算を要求ラインに置いたとき）
```

T=15万・予算1万・帯ROI 0.75 なら **1レースあたり 5.0% が天井**。
7T1 の実測は **3.04%** で、天井の **61%** しか使えていない。

🔴 **券種・点数・配分を変えても天井は動かない。** 点数を増やすと要求オッズが同率で
上がって相殺する。実測でも 7車三連単の帯 ROI は 15-30倍 75.0% / 30-60倍 73.0% /
60-90倍 76.2% / 150-300倍 71.1% / 300-600倍 73.2% と**裾までフラット**＝
市場は三連単の高配当帯でも効率的で、帯の選択では勝てない。

### 6.1 🟢 レバーA — 目標到達率（天井の61%→?）

7T1 の**的中の 66.2% しか目標額に届かない**（`keirin/CLAUDE.md` 7T1節）。
理由は選別が**予測**オッズ、払戻が**確定**オッズだから。
`odds_tf_meta.json` の実測で **`under08` = 42.1%**（確定/予測 < 0.8）・
`under05` = 10.7%。つまり4割の目が予測より2割以上安く決まる。

→ **目標判定を予測オッズの点推定ではなく下限側で行う**（三連複の
`_conservative_trio_board` に相当するものが三連単には無い）。
マージン m を掛けて `pred_odds >= (T/stake) × m` で選ぶ。

- 効果の向き: 到達率 66.2% → 改善 / 的中率 → 低下（要求オッズが上がるため）
- **積 P(>=T) がどちらへ動くかは測らないと分からない**。天井の61%という余白は
  そのぶん存在する
- 🔴 **ROI は動かない前提で測ること**（帯ROIがフラットなので）。
  見る指標は **T超/日** と **100%超の日**
- 既存ハーネス: `scripts/exp_highpay_odds_drift.py`（三連単の朝→最終ドリフト監査）

### 6.2 🟡 レバーB — 本命バスト確率による 7T1 のレース選定

唯一「市場に無く、市場と逆を向いている」ことが実証された予測
（`lgbm_wt_bad` 系・本命が4着以下に飛ぶ・AUC 0.6837〜0.6848）。

- 7H1 はこれを**買う側**（本命が飛ぶ前提の穴）で使っている
- 7T1 は軸1を1着に固定するので、**本命バストは損失要因**。つまり
  **バスト確率が低いレースを選ぶ**という逆向きの使い方は未検証
- 🔴 7T1 の既存の否定結果「荒れ指標（軸積・top3合計・エントロピー）でのレース選定は
  全滅」に**バスト確率は含まれていない**。あれらは自モデルの確率集中度＝市場と
  同じ向きの量で、バスト確率はそうではない
- ⚠️ ただし三連複3点へ当てたときは ROI 74.6% で壁を出せなかった
  （[[keirin_trio3_roi100_infeasible_2026_08_11]]）。**券種が変われば結果も変わる**
  とは限らないので、期待値は低めに置くこと

### 8.2 🔴 変更時に必ず守ること（過去に踏んだ罠）

1. **`T` と `N` を別々に動かさない。** `T = N × 10,000` の自己整合を崩すと
   「当たっても日次がプラスにならない」か「当たる回数が足りない」のどちらかになる
2. **確率の絶対閾値を新設しない。** 前身 7H3 は「軸積 >= 0.70」で切ったため
   確率の出どころが変わった瞬間に母集団が1.4倍になり崩壊した。
   7T1 は確率を**相対順位でしか使わず**、閾値は予測オッズ側に置く設計を守る
3. **日次上限は必ず `race_date` ごとに掛ける。** `build_7t1_candidates.build` は
   バックフィルから月単位で呼ばれるので、一括で掛けるとその月ぜんぶで N 件になる
4. **`rank_rule_version` は判定定数から自動導出**される。手で採番しない
5. **定数を変えたら `rebuild_7t1_walkforward_pg.py` で過去分を作り直す。**
   やらないと Web の実績と実際に売る商品の性格が食い違う
6. **モデル配布とコード投入のタイミングを合わせる**（`scripts/sync_models_to_vps.sh`）
7. **`keirin/CLAUDE.md` と `docs/prediction-factors.md` / `docs/bet-structure-guide.md`
   を同時に更新**（CLAUDE.md 冒頭のドキュメント更新ルール）

### 8.3 効果測定の作法

🔴 **ROI で採否を決めない。** 7T1 帯は月次 ROI が 62〜140% に振れ、
CI を ±2.5pt に収めるには約15年かかる（7M1 の実測）。
判断は **100%超の日 / 0円の日 / T超の頻度** の3つで行い、ROI は下振れ検知に使う。

🔴 **確認窓は結果を見る前に母集団の同一性を確かめる**
（選出率・ゲート通過率・ベースラインKPIを本番窓と突き合わせる）。
[[keirin_verification_design_audit_2026_08_21]] で、確認窓の79%が別母集団だったために
誤って「棄却」を宣言した事例がある。

🔴 **採用候補は vintage を替えて先に確認する。** 効果量が vintage 1本で
+2.81pt → +0.26pt へ消えた実例がある。

## 10. 中央の `market_agree` は競輪へ移せるか（2026-08-22・**未採用**）

ユーザー要望「中央は指数が市場と同等の情報しか持っておらず、市場を上回るために
**組み合わせの見直し**で改善したらしい。競輪でも同様の効果がないか」。
ハーネス: `scripts/exp_market_agree_wt.py`

### 10.0 そもそも往復している

中央の `market_agree` は **競輪の S1 軸級班 deny 手法を移植して生まれた**
（[[jra_axis_market_agree_redesign]] 冒頭）。競輪側は既に `wt_overlap_n`
（モデル上位2車が**公式予想印 ◎○** と一致するか）を **7S / 7B / 7M1 のランク定義
そのもの**にしている。⚠️ ただし見ているのは**印＝予想家の意見**で**市場ではない**。

### 10.1 🟢 信号は実在する（確定オッズ・14,922R）

競輪には単勝の板が無いので周辺化で作る:
`市場p3_i = 3 × Σ_{c∋i}(1/o_c) / Σ_c(1/o_c)`（trio 板）/
`市場pw_i = Σ_{j≠i}(1/o_{i-j}) / Σ(1/o)`（exacta 板）。

| 指標 | ランク | 一致 的中 | 乖離 的中 | Δ [95%CI] |
|---|---|---|---|---|
| 軸2車==市場p3上位2 | 7C | 40.5% | 21.4% | **+19.1pt [+13.7,+24.3]** |
| モデルp3 1位==市場p3 1位 | 7S | 45.1% | 32.1% | **+13.0pt [+7.0,+19.4]** |
| モデル1着率1位==市場1着率1位 | 7B | 32.4% | 23.7% | **+8.7pt [+2.0,+15.6]** |

🔴 **中央と同じ形で、的中率は割れるが ROI は割れない。**

### 10.2 🔴 だが入稿時点に本物の市場が無い（中央との構造的な違い）

- `wt_odds` は**レース後に1回だけ**収集される確定オッズ
- `wt_odds_snapshot` の `morning` は **07:03 収集・入稿開始 07:09** でタイミングは
  間に合うが、**市場として成立していない**: 7車の **61.3%** にしか板が無く
  （13時以降発走のレースには**存在しない**）、あっても三連複 **35点中 平均21.4点**。
  収集開始も 2026-06-08 から。
  **ユーザー判断: 「実オッズはまだ正当なオッズになっていないので予測オッズのほうが
  筋がいい」→ 現行の予測オッズ運用が正しい**
- 🔴 予測オッズ板は `predict_board(p3, pw, meta)` ＝ **モデル自身の確率が入力**。
  そのため「モデル vs 予測市場」は **96% 一致**し乖離群が **3.7%** しか取れない

### 10.3 残る実用効果は約1pt

`agree_p3_top2` が False のレースを買わない deny（予測オッズ）:

⚠️ **部分集団の分離幅（+24pt）と商品への効き幅（+0.9pt）を混同しないこと。**

### 10.4 ❌ 乖離を連続量にする案は不成立

model_p3 と market_p3 の L1距離で5分位に切ると **7C/7S/7B/7M1 の4ランクすべてで
完全に平坦**（Q5−Q1 の CI が全て0を跨ぐ）。**二値の稀な不連続にしか情報が無い。**

### 10.5 🔴 7M1 では符号が逆（一律適用は不可）

朝オッズ実測で `agree_p3_1` Δ的中 **−7.3pt [−13.6,−0.8]** /

### 10.6 採否

**未採用。** +0.9pt は有意だが小さく、**63セル**（3指標 × 7ランク × 3市場定義）を

## 12. 中央 v27 と同じ「既存データの組み合わせ見直し」は競輪で効くか（2026-08-22）

ユーザー指摘「中央はオッズを見たのではなく、**既に取得済みのデータに対し組み合わせに
より的中を導き出した**」。中央 v27 の実体は

    旧: LGB LambdaRank 0.3 + v24線形和 0.7
    新: z_blend = z(−reg_rank) − 0.5 × z(out_probability)   ← 2ヘッドの合成
    → 1位馬勝率 27.08→28.40% / レース内 Spearman 0.4783→0.5094（**オッズ不使用**）

ハーネス: `scripts/exp_leg_prob_heads.py`

### 12.1 競輪側の穴 — 三連単の買い目確率が1ヘッドしか使っていない

競輪は4ヘッドを持つ（`lgbm_wt_eval`=3着内率 / `lgbm_wt_win`=1着率 /
`lgbm_wt_bad`=大敗率 / `lgbm_wt_top2`=2着内率。**本番・vintage とも全て配備済み**）。
だが合成しているのは**軸2の選定だけ**:

    軸1 = pred_win 最上位                           ← 1ヘッド
    軸2 = z(pred_p3) − 0.3 × z(pred_bad)           ← 2ヘッド（v27 と同型）
    買い目 = rank_7t1_pl_prob(win_probs, leg)       ← **1着率のみの Plackett-Luce**

三連単の3つの着順すべてを**同じ強度ベクトル**で説明している。

### 12.2 🟢 確率としては明確に改善する（確認窓で再現）

位置ごとに強度を変える一般化 PL（`s_i = pw^a_i · p3^(1−a_i)`）を掃引:

| 案 | logloss | 実決着の中央順位(210通) | top1 | top3 | top6 |
|---|---|---|---|---|---|
| **現行 (1,1,1)** | 4.6176 | 20位 | 5.90% | 14.72% | 23.97% |
| **(1,.5,0) 後ろほど p3** | **4.2919** | **16位** | **10.50%** | **21.88%** | **32.20%** |
| (1,1,0) | 4.3460 | 17位 | 10.42% | 21.15% | 30.93% |
| 逆 (0,.5,1) | 4.7709 | 28位 | 1.82% | 9.57% | 17.93% |

**現行は試した中で最も悪い形**で、逆向きにすると更に悪化する＝方向に意味がある。
時間で分けた確認窓でも落ちない（掃引窓 Δtop1 +4.13pt / **確認窓 +3.60pt**・
9案の順位が両窓で完全一致）。

### 12.3 ❌ しかし商品には伝わらない

`exp_tf_shape_prod` と同じ出荷実装で 7T2 の KPI を測ると:

| 買い目確率 | 点 | 的中% | ROI | 15万+/日 | 100%超の日 |
|---|---|---|---|---|---|
| 現行（1着率のみ） | 1.73 | **3.01%** | 82.7% | **0.51** | **36.8%** |
| 新 (1,.5,0) | 2.93 | 2.82% | 82.4% | 0.47 | 34.6% |
| 新 (1,.5,0)・点数を揃える | 2.35 | 2.80% | 90.0% | 0.49 | 35.5% |

🔴 **機序: 7T1/7T2 は「オッズ15〜75倍の裾」しか買わない。**
改善したのは「最も来やすい決着はどれか」というバルクの精度で、
**買う場所（裾）と噛み合っていない**。

⚠️ 素直に差し替えると**点数が 1.73 → 2.93 に増える**（確率が上がると足切りを通る目が
有望に見え、自己整合の点数選択がより多く採る）。
[[keirin_position_disadvantage_verification_2026_08_03]] の
「確率を触る変更はそれを入力にするゲートの分布まで見る」の実例。

### 12.4 なぜ中央では効いて競輪では効かないのか

**中央の推奨は「指数1位馬」＝バルクの先頭を買う商品**なので、バルクの順位精度が
そのまま KPI になる。**競輪の一撃枠は裾を買う商品**なので同じ改善が伝わらない。
**同じ手法でも、商品がどこを買っているかで効く/効かないが決まる。**

### 12.5 🟡 正しい適用先は三連複ランクの相手選択（未検証）

競輪でバルクを買っているのは 7C / 7S / 7B（的中時中央 1.5〜2.3倍）。
これらの相手選択は `RANK_7C_LEG_P3_MIN`（3着内率 0.15 以上）という
**単一ヘッドの閾値**で、`bad` も `top2` も使っていない。
ここが v27 と同型の適用先。

🔴 **やるときは最初から出荷実装で測ること。** 本セッションで
「簡易実装で 8/8 勝ち → 出荷実装で逆転」を既に1回踏んでいる（§4.0）。
⚠️ キャッシュに `bad` / `top2` が入っていないので、`exp_tf_shape_cache.py` に
   2ヘッド追加して作り直すところから。

## 13. 三連単210通りの粒度に妙味はあるか（2026-08-22・❌ 買う帯では無い）

ユーザー仮説「三連単も点数が多い分ギャップが発生し、適切に買い目を絞れると

値付けしきれず残差が出るのでは、という問い。
ハーネス: `scripts/exp_tf_leg_gap.py`

### 13.1 なぜ今なら測れるのか

§12 で買い目確率を位置別合成 `(1,.5,0)` へ替えると
top1 5.90→10.50%（確認窓でも再現）と明確に良くなることが分かった。
**まともな確率が無ければ EV は測れない。** その改善した確率で
`EV = p_model × 予測オッズ` を作り、**確定オッズで採点した実現 ROI** を見る。

### 13.2 母集団全体では勾配があるように見える（が交絡）

極端な大穴の値付けが悪い（favorite–longshot bias）ぶんが勾配に見えている。

### 13.3 ❌ 実際に買う帯（15〜75倍）では完全に平坦

| EV分位 | 目数 | 的中率 | 平均予測オッズ | 実現ROI | CI95 |
|---|---|---|---|---|---|
| Q1 | 48,184 | 2.225% | 43.5 | 75.2% | [70.1, 80.5] |

## 16. レース選別は「不可能」ではない — だが p3 由来の形は市場が織り込む（2026-08-23）

ユーザー指摘: §15.4 で「レース選別は効かない」と結論したが、それは

## 28. ❌「入着困難なら次点を軸1へ繰り上げる」は成立しない（2026-08-23）

ユーザー提案:

`keirin/scripts/exp_axis1_swap_by_bustrisk.py`。**両方向の独立窓で否定された。**

### まず構造: 三連複では「繰り上げ」自体が no-op になりうる

二軸的中は**順序ではなく集合**で決まる。次点を軸1へ繰り上げても軸2を `p3` で
選び直せば残りの最上位＝**元の軸1**が入るので、ペアは `{1位,2位}` のままで
現行と完全に同一。効果が出るのは ①元の軸1を**ペアから外す**（`{2位,3位}`）か
②**順序が意味を持つ三連単**の場合だけ。両方を測った。

### どの帯でも 1位 > 2位（差は縮むが**一度も逆転しない**）

バスト検出器の十分位＋極端な尾（上位5%/2%/1%）で切った、p3順位ごとの

| 上位2%（最も危険） | 60.2% / 27.8% | 53.2% / 21.7% | 48.2% / 17.4% |

「2位 − 1位」の差は **D1 −17.07pt → D10 −4.88pt** と縮むが、
**全13帯・両窓で一度も正にならない**。最も危険な上位1%でも

ペアの集合で比べても同じ:

| 帯 | `{1,2}` 現行 | `{2,3}` 繰り上げ | Δ |
|---|---|---|---|

### 28.1 補足: フォーメーション（相手複数・1位を相手に置く）で測り直した

§28 は**ペアの二軸的中**だけを見ていたので、指摘どおり**積で**測り直した

    三連複の的中 = P(軸2車がともに3着内) × P(相手のどれかが残り1枠 | 軸的中)

| 腕 | 軸2車 | 相手（N点・p3順） |
|---|---|---|
| 現行 | `{1位,2位}` | 3位,4位,5位,6位,7位 |
| 繰り上げ | `{2位,3位}` | **1位**,4位,5位,6位,7位 |

賭け金は `unit_stake(N)` なので**総額はどちらも同じ**＝点数を揃えた公平な比較。

🟢 **N=1 では両者が完全に一致する**（`{2,3}+1位` = `{1,2,3}`・的中もROIも小数点まで同値）。
ハーネスが正しく組めている証拠であり、**同時に §28 の構造指摘そのもの**でもある。

### 🔴 なぜか — 「1位を外す」ではなく「3位を必ず入れる」ことになる

軸から1位を外すと、代わりに **3位が全ての買い目に必ず入る**。
3位の3着内率は危険帯でも 50.6%（1位 63.2% / 2位 58.3%）で、
**外した1位より 12.6pt 弱い車を、相手ではなく軸として固定する**ことになる。
1位は相手に回るので買い目のうち1点にしか乗らない。差し引きで必ず損をする。

### ⚠️ ただし ROI だけは危険帯で符号が逆（採用はしない）

| 帯・点数 | 検定26 ROIΔ | 検定24-25 ROIΔ |

| 上位10%・2点 | −1.9pt [−14.1,+9.9] | **+7.8pt [+0.0,+15.8]** 🟢 |

**片窓でしか有意にならない**ので、本プロジェクトの二窓ルールでは不採用。
中身も「より配当の高い目を買っているだけ」で、
§14・§25 で繰り返し確認した「オッズ帯を移して ROI が動いて見える」型に一致する。
**的中率は確実に下がるので、KPI（当たる回数）では純損**。

### 28.2 🔴 測り直し: 軸2を**ペアの相性で選び直す**形（ユーザーの設計どおり）

ユーザー再指摘:

    ■元の二軸  1. 指数1位を軸1に
              2. 軸1とラインなどで一緒に3着以内へ来やすい1車を軸2に
    ■提案      1. 指数1位が軸1にできそうにないレースでは指数2位を軸1に
                 （この時点で指数1位は**軸にしない**）
              2. 指数2位と一緒に来やすい1車を軸2に（**指数1位は候補から除外**）

🔴 **§28 / §28.1 は測り方を間違えていた。** 軸2を「p3の3位」に固定していたが、
提案は**ペアの相性で選び直す**。3位が最良の相方とは限らないので、
固定した時点で提案より弱い形を測っていた。**ペアモデルで測り直す**
（`keirin/scripts/exp_axis1_swap_pairmodel.py`）。

なお本番の軸選定は `strategy_wt.select_axes_*` が
**軸1 = `pw` 最上位 / 軸2 = `z(p3) − w·z(bad)` の最上位（軸1を除く）**。
ここでは指標を `p3` に揃え、軸2はペア同時確率の argmax で選ぶ。

### 結果: どの帯でも 1位を軸から外すと大きく負ける

## 32. 統一比較台の作り直し（2026-08-23・§30 の待ち行列 2 の前提整備）

`exp_unified_compare.py` は**3つの欠陥**があり結論に使えなかった。
`exp_unified_compare2.py` として作り直した（旧版には使用禁止の見出しを付けて残す）。

### 欠陥1: in-sample 混入 — 探索窓で学習して**同じ窓で**評価していた

```python
jm = fit(build_A(S, ...))        # 探索窓 S で学習
PS = build_pool(S, ..., jm, ...) # 同じ S を予測 ← in-sample
```

モデル系の腕（`AX_PAIR` / `LG_JOINT`）だけが持ち上がり、探索窓で ROI 106〜109% と
出て確認窓で崩れた。🔴 **表示が甘くなるだけでなく「選択そのもの」が壊れる。**

→ **探索窓は交差適合（out-of-fold）**。fold は **日で交互に**割る
（年や前後で割ると片側の学習窓が消え、結局 in-sample のスコアで層を切る）。
レース型の3分割しきい値（配当の3分位）も **fold の学習側だけ**から決める
（全 S から決めると、そのレースの配当が自分のブロック定義に混ざる）。
確認窓は S 全体で学習して C を予測する通常の hold-out。

実測の fold（vintage・549日）: 学習 25,916〜26,562R → 予測 8,401〜9,047R。
しきい値は 4.7〜4.8倍 / 15.1〜15.3倍 で fold 間に実質差なし。

### 欠陥2: 母集団不揃い — 別のレース集合の数字を1つの表で並べていた

構成ごとに落ちるレースが違うのに（`N_GAP` は7Cが買わないレースを落とす／
盤面に無い買い目／`AX_SWAP` の軸不成立）、ROI 降順の1つの表に並べていた。

→ **2枚に分けて、混ぜない。**

| 面 | 母集団 | 答える問い | ROI を横に比べてよいか |
|---|---|---|---|
| **A 対応比較** | **全構成が買えるレースだけ** | 買い方としてどのルールが優れているか | ✅ よい |
| **B 体系値** | 実母集団（見送りは投資0） | ポートフォリオとして1円あたり幾ら戻るか | ❌ **いけない**（絞れば上がる） |

さらに **盤面に一部しか無い場合も「買わない」扱い**に変えた
（旧版は在る目だけ買って点数を変えており、構成ごとに別の商品になっていた）。
選択は **A面の「現行相当との差」＋日ブロック bootstrap** で行う
（絶対 ROI の降順で選ぶと試した構成の数だけ多重比較になる）。

### 欠陥3: `LG_JOINT` が軸を動かす構成で**黙って `LG_P3` に退化**していた

スモークで `AX_SWAP/LG_P3/N4` と `AX_SWAP/LG_JOINT/N4` が**完全に同じ数字**に

統一した。`frozenset(3車)` をキーにするのでどの軸でも引ける。
🔴 **フォールバック発生率を毎回出す**（現在 0.000%）。

**保存していないものは復元できない**という話。

### 🔴 結論と、事前登録への申し送り

**事前登録 Phase 0 の完了条件「現行の優先順位方式を再現して現行実績と一致すること」は
取り下げるしかない。** 代替案:

| 案 | 中身 | 評価 |
|---|---|---|
| **A（推奨）** | プールを **vintage 再構築**と定義し、**「現行相当」も同じ vintage 再構築で作る**。全ての腕を同じ土俵に載せ、**実入稿とは一致しないことを明示して受け入れる** | 内部整合が取れる。§32 の比較台は既にこの形 |
| B | 候補JSONをプールにする | 忠実だが **s7 で 2026-07-27〜** しか無く、事前登録の窓を覆えない |
| C | 今後 候補JSON＋モデル版を保存し、前向きに貯めて後日きれいに比較する | 正しいが**今日から数ヶ月かかる**。A と併用すべき |

🔴 **A を採るなら「現行相当」は実際に売った商品ではない**ことを常に明記すること。
比較は「買い方ルールの優劣」であって「現行商品の実績との比較」ではない。

### 🟢 併せて分かった構造的な問題（別途直す価値がある）

**同じレースの3着内確率が3つ存在し、どれも一致しない。**

1. `wt_entries.pred_top3_pct` — Web表示・他ランク・分析が読む
2. 候補JSON の中の `pred_prob` 由来の値 — **ゲートが実際に使う**
3. backfill の再計算 — picks_history（＝Web の実績表示）が使う

Web が出している指数と、その指数で選んだと称する商品と、その商品の実績が
**それぞれ別の数字**で動いている。⚠️ 本節はこれを**発見しただけ**で、
影響範囲は測っていない。

CLAUDE.md「実験スクリプトの定数から baseline を取らない」の変種。
危うく「上限は効いていない」と**逆の結論を報告するところだった**。

**変わらなかったら、まず自分のパッチを疑うこと。**
