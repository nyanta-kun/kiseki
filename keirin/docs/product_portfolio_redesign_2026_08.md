# 商品体系の再設計（7車）— 事前登録

作成 2026-08-23。ユーザー指摘:

> 1レース1推奨（1万円配分）となるため、商品を複数作る場合も条件を分け競合しない
> ように組み立てる方がベスト。現在のベースはその設計がうまくできておらず、
> 優先順位で商品分けをしている。体系的（指数1位を軸1とするケースと、指数1位を
> 二軸に含めないケース、など）に商品を分ける構成と比較し、商品総合での
> 1日の ROI 最適化を検討したい。

🔴 **本書は着手前の事前登録である。** 目的関数・窓・分割軸・採否ラインを
**結果を見る前に**固定する。これを書く理由は
[[keirin_verification_design_audit_2026_08_21]] と本日の2件の設計ミス
（§28 の設計誤読 / §29 の点数未確認）で、いずれも
**実験設計の前に本番コードを読んでいれば防げた**ものだった。

## 1. 何が問題か（実装に証拠がある）

netkeirin は **1レース1商品**しか売れないため、`RANK_ORDER`
（7H2 > 7S > 7B > 7C > 7T1 > 7H1 > 7M1）で重複を落としている。
その結果、商品の中身ではなく**優先順位が売るものを決めている**。
`strategy_wt.py` の 7S の記述:

> 競合は **2,710R ＝ 7S の 84%** ＝ この優先順位が 7S 商品のほぼ全体を決める

🔴 **したがって現行の商品別実績は、すべて「上位商品が取った後の残り」で測った
条件付きの値**であり、新体系へそのまま持ち込めない。比較には
**優先順位をかけない共通の候補プール**が要る（Phase 0）。

---

## 2. 目的関数（2026-08-23 ユーザー決定: 日次ROI ＋ 的中率の下限）

1レース1万円なので:

    日次ROI(d) = Σ払戻(d) ÷ (件数(d) × 10,000)
    体系ROI    = Σ払戻 ÷ Σ投資     （日ブロック bootstrap で CI を取る）

**制約**: 体系全体の的中率が**現行体系の同一プール上の的中率を下回らない**こと。

🔴 **「現行水準」は現行の公表値ではなく、Phase 0 の共通プール上で
現行の優先順位方式を再現して測った値**を使う（条件付きの値と比べないため）。
🔴 **件数は選択変数**。見送りを明示的な選択肢として扱う。
⚠️ **日次上限（`RANK_7S_DAILY_TOP_N` 等）は評価時に一度すべて外す。**
上限があると「厳選が効いて見える」選択効果が入る
（[[keirin_trio_partner_and_axis2_2026_08_23]] で実際に踏んだ）。
上限は体系が決まった後に、別途の設計変数として戻す。

## 3. 検証窓（2026-08-23 ユーザー決定）

| 区分 | 期間 | 使い方 |
|---|---|---|
| 探索 | **2024-01-01 〜 2025-12-31** | 分割軸・買い方・閾値をここで決める。何度見てもよい |
| 確認 | **2026-01-01 〜 2026-06-30** | 探索で決めた構成を**そのまま**当てる |
| 封印 | **2026-07-01 〜 2026-08-22** | **最終判断のときに一度だけ開ける** |

⚠️ **封印窓の鮮度についての正直な但し書き。** 2026年は本日 §24〜§29 で
確認窓として繰り返し使った。閾値をこの期間で選んだことは無いが、
集計値は既に見ている。**完全に新鮮な窓ではない。**
→ 真に清潔な最終確認は **2026-08-23 以降に貯まる前向きデータ**であり、
実装期間中にそれを貯めて最後に当てるのが最良。封印窓はその代用と位置づける。

## 4. 手順

| Phase | 内容 | 完了条件 |
|---|---|---|
| **0** | **共通候補プール**を作る。全7車レースについて、優先順位を一切かけずに全商品の買い目・投資・払戻を生成 | 現行の優先順位方式を再現して現行実績と一致すること（**一致しなければ以降は無意味**） |
| **1** | 分割軸を事前登録（下記 5）。セルを定義 | セルが**排他かつ網羅**（どのレースもちょうど1セル） |
| **2** | 各セルで買い方を決める（総流し / 絞り / 三連単 / 見送り） | 探索窓のみで決定 |
| **3** | 確認窓で評価 → 通れば封印窓を一度開ける | 下記 6 の採否ライン |

🔴 **Phase 0 の一致確認を省かないこと。** プールが現行を再現できないなら、
その後の比較はすべて別物を比べていることになる。

| A | **`p3` の集中度**（entropy / axis_sum） | §27 で最強の分離。32特徴の学習器がこの1本に負ける。既存ゲートも実質これ |

## 6. 採否ライン（事前登録・事後に動かさない）

新体系が現行体系に勝ったと言うには、**確認窓で以下をすべて満たす**こと:

1. 体系ROI の差 の 95%CI 下限 > 0（日ブロック bootstrap）
2. 体系の的中率が現行体系 − 1.0pt 以内（目的関数の制約）
3. 件数が現行の 0.8 倍以上（極端に絞って ROI を作る形を排除）
4. **探索窓と確認窓で符号が一致**

封印窓では 1 と 2 のみを見る（件数はそこで調整しない）。

## 6.5 🔴 Phase 0 の完了条件について（2026-08-23・**ユーザー判断待ち**）

監査（台帳 §33 / `scripts/phase0_pool_audit.py`）で、**完了条件
「現行の優先順位方式を再現して現行実績と一致すること」は字義どおりには
達成できない**ことが分かった。

🔴 **2026-08-23 追記・訂正（台帳 §34）**: 当初「原因はモデル版の違い」と書いたが
**測ったら違った**。本番モデルで作り直しても一致は 57.2%→**58.2%** としか動かない。

- 真の原因は **入稿と再構築が別経路**。入稿は `cli/main.py` が朝に書いた
  **候補JSON**を読み、`backfill_*_rank_wt.build_rows()` は**後からDBを組み直す**
- 実測: `20260815_22_04` は `s7_candidates.json` に**在る**のに backfill の 7S 出力に**無い**
- 前例あり（`backfill_7c_rank_wt.py` docstring: 本番の3仕様が backfill に無く
  84件中17件で点数が食い違った）
- なおモデル版の差も**残差としては存在する**（プールを本番モデルで作れば
  全期間 in-sample になるので、**プールは vintage のままにする**）

🔴🔴 **2026-08-23 さらに追記（台帳 §35）— 完了条件は原理的に達成できない。**
7S で突き合わせたところ候補レベルの一致は **34.9%** で、原因は
**ゲートが見た p3 がどこにも残っていない**ことだった:

- 同じレースで **候補JSON の axis_sum 1.2833 / entropy 1.8007** に対し、
  `wt_entries.pred_top3_pct` から計算すると **1.251 / 1.8577**（別の値）
- そして `lgbm_wt_eval.meta.json` の `trained_at` は **2026-08-21**
  ＝ 8月上旬の候補を作ったモデルは**もう存在しない**
- ❌ 日次上限（サブランクごとで一度も binding せず）・❌ 印の後変化（実測変化0件）・
  ❌ データ欠損（すべて揃っている）は**測って否定済み**

→ **`build_rows()` をどう直しても過去の入稿は再現できない。**

**推奨（採否は未決）**: プールを **vintage 再構築**と定義し、
**「現行相当」も同じ vintage 再構築で作る**。全ての腕を同じ土俵に載せ、
**実入稿とは一致しないことを明示して受け入れる**（§32 の比較台は既にこの形）。
🔴 その場合「現行相当」は**実際に売った商品ではない**と常に明記すること。
併せて、今後のために候補JSON＋モデル版を保存して前向きに貯める。

**旧提案（参考・0a は上記により実行不能と判明）**: 完了条件を2つに分ける。

| | 内容 |
|---|---|
| **0a 論理の一致** | **同じ p3 を入れたとき**プール側のゲートが入稿側と同じ判定を出すこと |
| **0b 被覆** | 両窓で全ランクにプール行があること（🔴 現状 `7H2` `7T1` がゼロ） |

そして **Phase 1 以降は vintage プールの上で比較する**（入稿実績の上ではない）。

⚠️ 0b を閉じるには `rebuild_7h2_walkforward_pg.py` / `rebuild_7t1_walkforward_pg.py`

## 7. 作法（本日の失敗の是正）

実験を設計する前に、対象商品について**本番コードを読んで**次の3点を書き出す:

1. **その商品が実際に何点買うか / 候補は何車か**
   （§29: 7C が5候補中4〜5点を買っていることを確認せずに移植先に推奨した）
2. **母集団は何か**（どのゲートを通ったレースか）
3. **変更が動かす指標は何か**（的中か ROI か件数か）

🔴 **「効果があった」と「その商品に効く」は別**。
§24 の +1.6pt は「5候補から1点」の値で、4〜5点買う 7C には原理的に伝わらなかった。

## 9. レース型の3クラス分類（2026-08-23・実測）

ユーザー方針「商品を分ける前に、オッズ公開前のデータだけで
硬い／混戦／荒れ を分ける精度を作る」。`scripts/exp_race_regime_3class.py`

### 前提の監査（済み）

`FEATURE_COLS_WT`（66特徴）に**オッズ由来の列は無い**。市場に近いのは
`prediction_mark`（winticket AI印）だけで、これもオッズ公開前に出る。
→ 「オッズ公開前のデータのみ」という前提は**成立している**。

### 結果（探索 2024-01〜2025-12 → 確認 2026-01〜06 / 封印は未読）

定義P（三連複配当の3分割・しきい値は探索窓で決定: **< 4.8倍 / < 15.2倍 / 以上**）:

| クラス | 1対他AUC | 予測ブロックの的中精度 | 基準率 |
|---|---|---|---|
| 硬い | **0.7278** | 48.0% | 31.0% |
| 中（混戦） | 0.5967 | 41.3% | 34.6% |
| 荒れ | 0.6234 | 44.3% | 34.4% |

定義I（我々の指数基準）でも同傾向（硬い 0.6977 / 中 0.6073 / 荒れ 0.6535）。

### 🔴 分離は「的中率」には出るが「ROI」には出ない

**同じ買い方**（7C風・軸2車＋p3足切り）を全ブロックへ当てたとき:

| 予測ブロック | 件数 | 的中% | ROI | 中央配当 |
|---|---|---|---|---|
| 硬い | 2,434 | **62.49%** | 78.0% | 5.1倍 |
| 中（混戦） | 3,043 | 42.33% | 79.1% | 10.5倍 |
| 荒れ | 3,317 | 41.91% | **75.4%** | 12.5倍 |

🔴 **的中率は 62.5% ↔ 41.9% と大きく割れるのに、ROI は 75〜79% で平坦。**
しかも**荒れブロックが最低**で、ユーザーの理想「不人気で高回収率」とは逆向き。
[[keirin_irregular_layer_screening_2026_08_20]] の
「高配当は市場が約15%過大評価」と整合する。

→ **分割それ自体では ROI は動かない。ブロックごとに買い方を変えて初めて意味を持つ。**
   そのための統一比較台が `scripts/exp_unified_compare.py`（下記10）。

### 寄与上位

`p3_std` / `p3_ent` / `rp_std` / `p3_sum` / `p3_2` / `top1_rp` / `field_r1_mean`
＝ **本命がどれだけ抜けているか**と**メンバーの実力ばらつき**。
§27 で「32特徴の学習器が `p3` エントロピー1本に負ける」と出たのと同じ量。

## 10. 構成の統一比較台（2026-08-23・ユーザー指摘）

> 比較の統一も整備できていない。本日対応分の ROI は二軸総流しになっていそうだが、
> 相手の選別も元の検討に入っていた。適切に選別し、**相手点数を可変**、
> **投入金額が変わることを考慮**した比較が必要。

🔴 **そのとおり。** 本日の測定は §24=1点買い / §28.1=N点フォーメーション /
§28.2=ペアの的中のみ / §29=7C形 と**買い方がバラバラ**で横に比べられなかった。

`scripts/exp_unified_compare.py` で1枚の台に載せ直す。

    構成 = 軸ルール × 相手ルール × 点数ルール
      軸  : AX_P3（指数1・2位）/ AX_PAIR（ペア同時確率の argmax）/ AX_SWAP（2位軸・1位除外）
      相手: LG_P3（p3降順）/ LG_JOINT（三者同時確率降順）
      点数: N1〜N5（固定）/ N_GAP（7C の落差カット）

**投入金額の扱い**（指摘の核心）:

    ROI = Σ払戻 ÷ Σ投資      Σ投資 = Σ(点数 × unit_stake(点数))

点数で1点あたりの賭け金が変わり（端数切捨てあり）、構成によって**買わないレースが出る**
ので件数も変わる。**件数・Σ投資・1日あたり投資を必ず併記する。**

手順は事前登録どおり: 探索窓で全構成を出しブロックごとに最良を選ぶ →
確認窓で**選んだ構成だけ**を当てる → 封印窓は読まない。
