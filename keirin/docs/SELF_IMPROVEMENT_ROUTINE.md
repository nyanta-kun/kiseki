# 型ラボ 自己改善ルーチン — 計画・設計書

作成: 2026-09-23 / 状態: **設計（未実装）** / 正本: このファイル

買い目の選び方（レース条件・出走メンバ・展開）を組み換えて、1 日の払い戻しを大きくする。
それを毎日の解析と通知で回す仕組みの設計。**実装前に、何を毎日やり、何を毎日やらないかを固定する**のが目的。

---

## 0. 先に結論

| | 頻度 | 中身 |
|---|---|---|
| **半日ごと（14:00 / 22:00）** | 1日2回 | **予測の精度**（予測オッズ誤差・確率の較正）の監視、当落傾向の解析、異常検知、仮説の Discord 通知 |
| **毎日やらない** | — | 本番ルールの自動変更。仮説は通知し、採否は人が決める |
| 週次 | 日曜 | 精度指標のトレンド、paper 変異の比較（導入後） |
| 四半期 | TEST 窓 | `keirin_protocol` に沿った一度きり評価 → 昇格 |

🔴 **監視の主対象は ROI ではなく「予測の精度」。** ROI は分散が大きすぎて日々の判断に使えないが、
精度は 1 日あたり数千点の観測があり**半日で測れる**。ここが改善すれば的中・回収へ伝わる。

## 1. 何を監視するか — 2026-09-23 の実測で決めた

### 1-1. ROI を日々の判断材料にしてはいけない（が、改善余地が無いという意味ではない）

実売の日次 ROI は **sd 0.374**・プラスの日は 47 日中 4 日（8.5%）・中央値 0.63。
ここから ROI +0.05 の検出には約 220 日かかる。**日々の ROI 変動はノイズ**。
ただしこれは「ROI という*指標*の検出力」の話で、**予測精度の改善余地とは別**。

### 1-2. 1 車ごとの確率は概ね合っている（＝ここは伸びしろが小さい）

直近 90 日・32,174 観測（1 日 536 件）:

| 対象 | 予測 | 実測 | ずれ |
|---|---|---|---|
| 3着内率 全体 | 42.48% | 42.21% | **+0.27pt** |
| 予測帯 80-90% | 84.3% | 85.9% | −1.7pt（誤差幅 ±1.3） |
| 公式印 △(4) | 39.3% | 37.6% | +1.7pt（誤差幅 ±1.2） |

95%CI を外れるセルは 4 つだけ・幅は 0.6〜1.7pt。**1 車ごとの較正は大きく壊れていない。**

### 1-3. 組み合わせ確率も概ね合っている

買い目 1 点ごとの `prob` と実際の的中（47,229 点・90 日）を帯別に突き合わせると、
ほとんどの帯でずれは誤差幅の内側（最大 −0.96pt / 帯 4.7%）。

### 1-4. 🔴 ずれているのは**予測オッズ**。しかも向きが結果と相関している

買った全点（21 日・39,652 点）で確定オッズと突き合わせた:

| 区分 | 点数 | 確定 ÷ 予測（中央） | p25 | p75 |
|---|---|---|---|---|
| **外れた目** | 38,632 | **1.138** | 0.826 | 1.572 |
| **的中した目** | 1,020 | **0.862** | 0.630 | 1.136 |

予測オッズは一方向に偏っているのではなく、**当たる目ほど締まり、外れる目ほど流れる**。
締切までの資金移動が持つ情報を、朝に入稿する現行の買い目は取り込めていない。

🔴 **これは買い目の効率に直結する。** 点数・配分・ゲートはすべて予測オッズの上に乗っている:

- ダッチ配分は賭け金 ∝ 1/予測オッズ（`allocate()`）
- A/B/C_hit は「どの目でも約5万円」になるまで詰める（`target`）
- 入稿ゲートは平均想定払戻 2万円超（`MIN_MEAN_PAYOUT`）・全点 2.0 倍以上（`MIN_POINT_ODDS`）

当たる目が中央で 14% 締まるなら、**「どの目でも5万円」の設計は実際には約4.3万円で着地する**。
ゲートも 14% 甘い側で判定していることになる。

**帯で勾配がある**（確定÷予測の中央値・14日 31,335点）:

| 予測オッズ帯 | 〜20倍 | 20-50 | 50-100 | 100-300 | 300倍〜 |
|---|---|---|---|---|---|
| 確定÷予測 | 1.06 | 1.10 | 1.13 | 1.16 | **1.27** |

高オッズほど予測が低く出ている（＝実際はもっと流れる）。プラン別では `A_hit` が
最も締まる側（1.02）。**補正式を立てるならこの 2 軸（帯・プラン）から**。

→ **半日ルーチンの第一の監視対象はここ。** 1 日あたり約 2,000 点の観測があるので、
プラン別・オッズ帯別・会場別の系統誤差なら**半日〜数日で検出できる**。

## 2. 原則

1. **日次は観測と提案まで。本番反映は四半期ゲートを通ったものだけ。**
2. **変異は live を触らずに `mode='paper'` で前向きに走らせる。**
   `type_lab_picks` は `(race_key, plan_key, mode)` で一意なので、同じレースに
   live と paper を並べられる。**これが「in-sample にならない比較台」の唯一の作り方**
   （過去に遡って組み直すと `axis_sum` が 99.89% のレースで変わり、型ラベルが 6.04% で変わる
   ＝`type_lab.py::type_label_of` の実測）。
3. **個別レースの反実仮想を書かない。** 「あの 1 点を足していれば当たっていた」は
   日次レポートの禁止事項（`nightly_triage.sh` のプロンプトに既に明記）。
   組み換えの評価は**必ず母集団単位**で行う。
4. **事前登録する。** 変異は走らせる前に `docs/PREREG_*.md` を書く（既存の作法に合わせる）。
   後から条件を足して良く見えた組み合わせを採用しない。
5. **窓を焼かない。** 採否の評価は `keirin_protocol.assert_not_burned()` を通し、
   使ったら `record_test_usage()` で `docs/KEIRIN_TEST_USAGE_LEDGER.md` に残す。
   確認窓 2026-01〜08 は既に 50 本以上の検証で使い回されている（監査 §7.2）。

## 3. 組み換えの探索空間と目的関数

### 3-1. 動かすノブ（ユーザー要望の「レース条件・出走メンバ・展開」に対応）

| 区分 | ノブ | 現在値の所在 |
|---|---|---|
| レース条件 | race_type（決勝/準決勝/初日特選…）・グレード・車立て（7/9）・開催日次 | `type_lab.py` `SIGNBOARD_RACE_TYPES` / `HIGHPAY_TYPES` |
| 出走メンバ | 競走得点のばらつき `rp_sd`・級班構成・欠場/失格の有無 | gate `RP_SD_PRIORITY_AXIS_WEIGHT` |
| 展開 | ライン数・番手・`arare`（ライン形の点）・最強ラインの強さ | `type_lab.py` `BEHIND_MID = 11.0` |
| 型判定 | `AXIS_SUM_FIRM = 1.44`・`arare` の 3 分割境界 | `type_lab.py:73,651` |
| 買い目構成 | プランごとの券種・点数・相手の取り方 | `PLANS`（`type_lab.py:850`） |
| 配分 | `dutch` / `conf`・`MIN_PAYOUT_MULT = 2.0`・ダッチ目標額（A/B/C_hit = 5万） | `type_lab.py:126` ほか |
| 足切り | `AXIS_GATE_MIN`（7車のみ・8プラン）・`MIN_MEAN_PAYOUT = 20,000`・`MIN_POINT_ODDS = 2.0` | `keirin_type_lab_gate.py:155` / `stake_allocation.py:286,453` |
| 量 | `DAILY_CAP_RACE_FRACTION = 0.5`・`HIGHPAY_SLOTS_PER_DAY = 5` | gate `:344` / `type_lab.py:1536` |

⚠️ **5〜10 点という制約は予算と直結している。** `BUDGET = 10,000` / `UNIT = 100` は
netkeirin 側の制約で動かせない。点数を増やすと 1 点あたりが薄くなり、
`MIN_POINT_ODDS = 2.0`（全点 2 倍以上）と `MIN_PAYOUT_MULT = 2.0` に当たって自動的に頭打ちになる。
**点数は独立に選べるノブではなく、配分と払戻床の従属変数**として扱う。

### 3-2. 目的関数（「1 日の払い戻しを大きく」の操作的定義）

単純な日次払戻の最大化は、分散の大きい方へ寄る（＝たまたま大きい日を作る買い方に倒れる）。
監査の KPI と整合させ、次の**辞書式**にする。

```
1. 制約: 日次 ROI の 60 日移動平均が現行から −0.03 を下回らない（劣化させない）
2. 制約: 表示的中率が現行から −3pt を下回らない（商品の見え方を壊さない）
3. 最大化: 10万円以上の的中の件数／日（＝監査が「売上に効く」と特定した段差）
4. 同点なら: 4万円以上の的中の件数／日
```

**3 を主目的に置く根拠**は監査 §11（弾力性ではなく段差が効く・10万+ 的中の翌日に売上が伸びる）。
ROI は「上げる対象」ではなく「壊さない制約」として扱う。

## 4. 仕組み

### 4-1. 半日ごと（14:00 / 22:00・専用 clone で自動実行）

14:00 は午前〜昼の確定分、22:00 はその日の全レース。既存の `nightly_review.sh`（00:10・
live の事実レポート）とは役割を分け、**こちらは精度と傾向の監視に特化**する。

```
14:00 / 22:00  Mac  lab_halfday.sh
   ├ ① 予測オッズの誤差            ★第一の監視対象
   │     確定 ÷ 予測 の中央値を 全点 / 的中 / 外れ 別、オッズ帯別、プラン別、会場別に
   │     （1 回あたり数百〜数千点の観測。半日で動きが見える）
   ├ ② 確率の較正                   1車の p3・pw、買い目1点の prob を帯別に
   ├ ③ 計画払戻と実払戻の乖離       「どの目でも5万円」の設計が実際に何円で着地したか
   ├ ④ ゲートの境界                 平均想定払戻2万円ゲートが、誤差込みで判定を誤った件数
   ├ ⑤ 当落の傾向                   層別（プラン内）+ FDR + 前後半一致を通ったセルのみ
   ├ ⑥ 異常検知                     欠測・素通し・採点の取りこぼし・rule_version の変更速度
   └ ⑦ Discord（review ch）へ 1 通
```

**⑤ の統計処理**（2026-09-23 に試作して決めた）:
素朴に「当たった条件／外れた条件」を並べると 132 セル中 57 セルが「有意」になった。
原因は (1) 多重比較 (2) プラン構成による交絡（会場ごとに走るプランが違う）。
→ **プラン内で比較して賭け金で加重**（層別）、**Benjamini-Hochberg で FDR 10%**、
**期間の前後半で同符号**、**paper の長期履歴と符号・効果量を突き合わせ**。
この 4 つを通すと 64 セル → 9 件 → 6 件に落ちる。

**⑦ 通知で禁止すること**（プロンプト・コードの両方で固定する）
- 個別レースの反実仮想（「あの1点を足していれば」）
- 参照分布の 5〜95% に収まる変動を「兆候」と書くこと
- 100 件未満のセルで採否を論じること
- 「今日の ROI が上下した」を根拠に何かを勧めること
- **長期の裏付けが実質ゼロ（|効果| < 0.02）なのに「裏が取れた」と書くこと**

### 4-1-1. 最初に追う仮説（1-4 から直接出るもの）

1. **予測オッズの条件付き補正**。当たる目ほど締まる（中央 0.862）なら、
   配分とゲートは「締まった後のオッズ」で計算すべき。まず**どの条件で締まり幅が大きいか**
   （オッズ帯・プラン・締切までの時間・会場）を半日ごとに測り、補正式が立つか見る
2. **点数と配分の再設計**。`target=5万` のダッチは予測オッズ前提なので、
   14% の締まりを織り込むと**同じ払戻を得るのに必要な点数が変わる**可能性がある
3. **ゲート閾値の実効値**。平均想定払戻 2万円ゲートは、実効では約 1.7万円で判定している

### 4-2. 週次（日曜・再学習の前）

paper 変異の順位表を更新する。列は
`変異ID / 稼働日数 / 件数 / 表示的中 / ROI [95%CI] / 10万+件数 / 4万+件数 / 対 live 差 [95%CI]`。
**稼働 100 日未満の変異は「評価不能」と明示**して並べる（消さない。消すと選択効果が入る）。

### 4-3. 四半期（TEST 窓・昇格の唯一の入口）

`keirin_protocol` に従う。**`MIN_TEST_WINDOWS = 4`＝1 年ぶんの TEST が要る**
（窓ごとの SD 0.15pt に対し追う効果量が +0.3pt 級のため。k=1 では実際に符号が反転した）。

昇格ゲート（**すべて機械判定・1 つでも落ちたら棄却**）:

| # | 条件 |
|---|---|
| 1 | 事前登録（`PREREG_*.md`）が変異の稼働開始より前に存在する |
| 2 | 探索窓（2024-07〜2025-12）と確認窓の**両方で同符号** |
| 3 | 日ブートストラップの 95%CI が 0 を跨がない |
| 4 | **点数を揃えた無作為対照 20seed に勝つ**（20/20 か、少なくとも 18/20） |
| 5 | TEST 窓 4 つで符号が一貫 |
| 6 | 3-2 の制約 1・2（ROI と的中率の非劣性）を満たす |
| 7 | 使用した窓が `BURNED_WINDOWS` に無い |

通過したものだけを `type_lab.py` の定数変更として PR にする。**PR には測定表をコメントとして残す**
（既存の `AXIS_GATE_MIN` docstring と同じ形式）。

## 5. 専用 clone を分ける理由と権限

**`~/GitHub/kiseki-dev/keirin-lab`（新規・自動実行専用）**

1. **自動実行と対話開発は同居できない。** `kiseki-dev/keirin` で作業中にブランチを切り替えると、
   その瞬間に日次ルーチンが別のコードで走る。
2. **共有キャッシュの書き込みは 1 つずつ**（`exp_cache` / `feature_cache` は 4 clone が同じ実体を見る）。
   日次ルーチンは決まった時刻に単独で走る必要がある。
3. **権限を絞る。** lab は「DB 読み取り」と「paper 行の書き込み」だけでよい。
   **netkeirin への入稿権限を持たせない**（`.env` から入稿系のキーを外す）。
   これで、ルーチンの暴走が本番の入稿に届かないことが構造的に担保される。

| clone | 役割 | 入稿 | live 行の書き込み |
|---|---|---|---|
| `~/GitHub/kiseki`（本番） | 実運用のジョブ | ○ | ○ |
| `kiseki-dev/keirin` | 対話的な開発 | × | × |
| **`kiseki-dev/keirin-lab`** | **日次ルーチン・paper 変異** | **×** | **×（paper のみ）** |

## 7. 未決事項

1. **paper 変異を何本まで同時に走らせるか。** 多いほど多重比較が効く。
   事前登録と合わせて**四半期あたり 8 本まで**を提案（監査 §4.2 の「21 プランの多重比較で
   有意が出た」失敗を繰り返さないため）。
2. **目的関数（3-2）の重み**。「10万+ 件数／日」を主目的にする案でよいか。
   ROI を主目的にすると控除率の壁に張り付いて動かない。
3. **通知の頻度**。毎日 1 通（review ch）で足りるか、異常時のみ system ch にも出すか。
4. **既存 `nightly_review.sh` / `nightly_triage.sh` との関係**。
   重複させず、lab 側は「変異の比較」に特化し、live の事実レポートは既存へ委ねる案を提案。
