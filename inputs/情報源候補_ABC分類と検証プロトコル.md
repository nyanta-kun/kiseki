## 0. 判断フレーム（再掲・確定版）

| 分類 | 定義 | ROI上限 | 扱い |
|---|---|---|---|
| **A** | 市場が既に読んでいる情報 | 75%（市場に追いつくだけ） | 収集しない。ただし**的中率商品としての価値はある**ため、ブランド訴求用に切り分けて扱う |
| **B** | 市場が処理しきれない行動バイアス | 81%（測定済み） | 実在するが小さい。既知として保持、追加投資しない |
| **C** | 誰も定量化していない情報 | 100%到達の唯一の道 | **ここに集中** |

Cの定義を厳密化する：**「市場が見てはいるが粗くしか処理していない」ものを精密に数値化する領域**。したがってC候補の要件は次の3つを同時に満たすこと。

1. 公開情報である（インサイダーではない＝合法かつ再現可能）
2. 人間のベッターが感覚・定性でしか処理していない（＝オッズに粗くしか反映されていない）
3. 履歴として蓄積・統計処理すると連続値になる（＝定量化の余地がある）

### パリミュチュエルに関する訂正

前回メモの「直前の資金流入を追う」は誤り。パリミュチュエルは**払戻が最終オッズで確定する**ため「安いうちに買う」が成立せず、オッズ変動から利益は出ない。この項目はAに還元する。
ただしオッズには別の用途がある：**市場の含意確率（implied probability）のベンチマーク**としては必須。全ての比の計算の分母になるため、確定オッズは引き続き必ず保持すること。

## 1. A分類（収集不要・確認のみ）

以下は取得しても市場に追いつくだけ。**新規の収集投資はしない。**

- 専門紙の記者印、予想印
- 選手コメント、前検日の評判・調子談話
- SNS上の予想・情報
- 直前オッズおよびその変動（上記の通りパリミュチュエルでは変動から利益が出ない）
- 競走得点の表示値そのもの、脚質区分、直近着順の表示値
- 地元開催かどうか（登録地＝ホーム。人間が最も分かりやすく織り込む変数）
- ライン並び予想（各社が公開しており完全に織り込み済み）

**ただし例外的に価値が残る使い方**：これらの「表示値」と、自前で構築した精密指標との**乖離（residual）**を特徴量にすること。表示値そのものはAだが、「表示値と真値の差」はCになり得る（→ C-5参照）。

## 2. B分類（既知・追加投資なし）

- 同ライン相関（人間はライン単位でまとめて買うため、スジ決着のオッズが相対的に安く、スジ違いが甘くなる）
- longshot bias

**補足（文献調査結果）**：欧米のパリミュチュエル市場ではlongshot bias（大穴が過剰に買われる）がほぼ普遍的に観測される一方、**日本と香港はこの例外として報告されている**（バイアスが観測されない、もしくは逆方向）。つまり「大穴が過剰人気なので本命側に妙味がある」という欧米の定石は日本市場では成立しない可能性が高い。

### C-1. 連戦負荷・遠征距離 【最優先・外部収集不要】

**なぜCか**：人間は「連戦で疲れている」「遠征帰りで動けない」を感覚でしか処理していない。斡旋（JKAによる出走場所の割当）と開催日程は公開情報で、選手ごとの出走履歴から移動距離・負荷が完全に再現できる。市場が粗くしか見ていない典型例。

**現状**：`days_since` が日数のみ。これを負荷ベクトルに拡張する。

**必要な外部データ**：競輪場43場の緯度経度のみ（一度作れば固定のマスタ）。それ以外は既存の出走履歴から計算可能。

**実装する特徴量**：

```
# 移動系
prev_venue_distance_km      # 前開催地→今開催地のhaversine距離
home_venue_distance_km      # 登録地（ホーム）→今開催地の距離 ※これ自体はA寄りだが交互作用用に必要
travel_burden               # prev_venue_distance_km / max(days_since_last_race, 1)
                            # ＝「短いインターバルで長距離移動」を1変数に圧縮
is_island_transfer          # 北海道・四国・九州・沖縄をまたぐ移動フラグ（陸路不可＝負荷が非線形に増える）

# 連戦系
races_in_last_30d           # 直近30日の出走回数
races_in_last_60d           # 直近60日
races_in_last_90d           # 直近90日
consecutive_series_count    # 開催間インターバルが N 日以内で連続した開催の連鎖数
                            # （N=3, 5, 7 でグリッドサーチ）
days_since_last_race        # 既存
day_in_series               # 開催内の何日目か（初日/2日目/準決/決勝）
cumulative_laps_in_series   # 開催中のここまでの出走本数（＝当該開催内の蓄積疲労）

# 交互作用
travel_burden × 脚質（先行かどうか）
                            # 先行選手は疲労の影響が非線形に大きいはずという仮説
travel_burden × day_in_series
races_in_last_30d × 年齢
```

**仮説の方向性**：`travel_burden` が高い先行選手は、市場の含意確率に対して実測が下振れる（＝買ってはいけない）。逆に低負荷の選手は上振れる。**下振れ側の検出も価値がある**点に注意（買い目から外すことで期待値が改善する）。

**注意点**：`days_since` が長い＝休養十分とは限らない。**落車・怪我による欠場明け**と**通常の斡旋間隔**は意味が正反対なので、欠場フラグ（斡旋されていたのに出走していない）で分離すること。分離できないと符号が相殺してノイズになる。

### C-2. 前検日の計測値 【調査結果：通常競輪では公開なし＝棄却】

**調査結果**：

- **通常の競輪（333/400/500mバンク）では、前検日に走行タイムの公式計測・公表は行われていない。** 前検日に行われるのは車体検査・公式検査であり、練習走行の様子は記者が定性的にレポートするのみ（＝これはA分類）。
- **例外：250競走（PIST6）では前検日にタイムトライアルが実施され、200mおよび100mのタイムが計測され順位付けされる**という審判要領上の規定がある。250競走を扱うなら数値ソースとして成立する。
- したがって本命の通常競輪では**「公開されていないので収集不可」**が結論。この候補にこれ以上の調査工数をかけないこと。

**代替として C-2'（ギア倍数）と C-7（上がりタイム）に振り替える。**

### C-2'. ギア倍数の履歴化・変化量 【❌ 実データ確認により棄却（2026-07-30）】

**棄却理由：ギア倍数はデータ上ほぼ変化しない＝変化量に分散が存在しない。**

| 測定 | 結果 |
|---|---|
| 連続出走日ペア 304,118件（2025-01以降・2,529選手） | **98.4%でギア不変**（変化 1.6%＝4,898件） |
| 変化時の \|Δ\| | 中央値 0.070 / 平均 0.051 |
| 全エントリの値の集中 | **72.8% が 3.92 の単一値** |
| 同一開催内で複数走した 36,721人 | ギア変動は 674人＝**1.8%** |

→ `gear_delta_prev` は98.4%がゼロ、`gear_delta_self_mean_90d` もほぼゼロ。
「今日は重いギアを入れてきたな」という現象自体がデータ上ほぼ発生していない。
**連続値の特徴量としては成立しない。**

**確認事項への回答**：`gear_ratio` は充填率100%で、**既に絶対値として
`FEATURE_COLS_WT` に採用済み**。前日発表値か当日変更後の最終値かの識別は、
上記の分散の低さから実質的に無意味（どちらでもほぼ同一の値になる）。

**残された唯一の使い方**：変化イベント自体は n=4,898 存在するので、
「ギアを変えてきた選手」の**2値フラグで市場比を1回測って打ち切る**。
連続値化・交互作用の設計に工数をかけないこと。

### C-2'（原文・記録として保持）

**なぜCと考えたか**：ギア倍数は**前日発表の出走表に数値で公開されており、当日変更時も場内放送・公式サイトで告知される**。つまり数値は完全に公開されている。しかし人間のベッターは「今日は重いギアを入れてきたな」と絶対値を感覚で見るだけで、**選手ごとの過去ギア履歴との差分、バンク別・季節別の平均からの偏差を統計処理している者はほぼいない**。定義上のC（見てはいるが粗くしか処理していない）に完全に合致する — という想定だったが、上記の通り前提（ギアが変化する）が成り立たなかった。

**実装する特徴量**：

```
gear_ratio                  # 当該レースのギア倍数（絶対値、Aに近い）
gear_delta_prev             # 前走からの変化量（＋＝重くした）
gear_delta_self_mean_90d    # 直近90日の自己平均からの偏差
gear_z_in_race              # 当該レース内での相対z-score（同レース他選手比）
gear_delta × bank_length    # バンク周長との交互作用（333で重ギアは意味が違う）
gear_delta × 脚質
gear_delta × 気温           # 夏場の重ギアは負荷が違うという仮説（C-3と結合）
```

**仮説**：ギアを重くする＝先行・逃げ切りに勝負をかけるサイン、軽くする＝回転で捲る/差す構え、と一般に語られる。この**変化の方向と決まり手の対応**が市場の含意確率にどこまで織り込まれているかを比で測る。特に「変化量」は誰も履歴を持っていないため、織り込み不足の可能性が高い。

**確認事項（Claude Code側）**：現行DBにギア倍数のカラムが存在するか、存在する場合の欠損率と、過去分の履歴が残っているか（当日変更が反映された最終値か、前日発表値か）を先に確認すること。前日値と最終値が混在していると変化量の意味が壊れる。

### C-3. バンク単位の実測気象×脚質 【条件付きで実施】

**データ源**：気象庁「過去の気象データ・ダウンロード」（https://www.data.jma.go.jp/risk/obsdl/）から、観測地点・要素・期間を指定してCSVで一括取得できる。全国約1300地点のアメダスで**時別の降水量・風向・風速・気温**が取得可能。競輪場43場それぞれに最寄りアメダス地点をマッピングするマスタを作れば、レース発走時刻に紐づけて結合できる。

**現状（2026-07-30 実データ確認により訂正）**：

⚠️ **「雨は検証すらできていない」は不正確。** G06（`scripts/exp_wind_wt.py`）は
`wt_weather` から **wind_speed / wind_gust / wind_dir / temp / precip の5項目すべて**を
取得し、束にして Phase1（AUC差 ±0.001 のゲート）で判定 → 不通過だった。
**雨(precip)・気温(temp)・風向(wind_dir) はいずれも検証対象に含まれていた。**

ただし以下2点で再検証の余地は残る:
1. **束での判定**なので、発生頻度の低い雨（年間数%）の効果は他4特徴に希釈された可能性
2. **`wind_dir` を生値のまま投入していた** → 下記の成分分解は真に未検証

⚠️ **`wt_weather` は現在 0 行**（カラム定義のみ）。G06 が使用したデータは失われており、
再検証には気象庁からの**再収集が前提**。

**風について（重要な留保・この指摘は技術的に正しい）**：G06 が投入したのは
`wind_dir` の**生値**であり、円環変数（0-360°）を会場ごとのバンク方位と結合せずに
木モデルへ入れても、会場別の向かい風方向を学習することは構造的に不可能。
したがって**否定されたのは実質「風速のスカラー値＋生の風向」であり、成分分解は未検証**。競輪で効くのは風速そのものではなく**ホームストレッチの走行方向に対する向かい風成分**のはずで、これはバンクの方位角と風向から分解できる。

```
headwind_component = wind_speed × cos(θ_wind − θ_homestretch)
```

バンクの方位（ホームストレッチが向く方角）のマスタが必要になるが、これは各競輪場の航空写真・地図から一度作れば固定。**スカラー風速で否定された仮説が、成分分解で復活するかどうか**は一度だけ測る価値がある。ここで比が1.00付近なら風は完全に打ち切ってよい。

**優先順位**：雨（未検証・テーブル0行）＞ 気温 ＞ 風の成分分解 ＞ 風のスカラー（打ち切り済み）。

```
precipitation_mm_1h         # 発走時刻の時間降水量
is_rain                     # 0.5mm/h以上フラグ
temperature_c
headwind_component          # 上記
is_rain × 脚質              # 雨は差し・追込有利という定説の定量検証
temperature_c × gear_ratio  # C-2'との結合
```

**期待値の見積り**：雨の発生頻度自体が低く（年間の数%）、セグメントのサンプルサイズが小さくなるため、有意差が出ても多重比較ノイズの可能性が高い。**測る価値はあるが、比が有意でもTRAIN/TEST両窓一致の要件は特に厳しく適用すること。**

### C-4. 機材変更・体重変動 【調査結果：棄却寄り】

**調査結果**：

- **体重・身長はKEIRIN.JPの選手プロフィールに掲載されているが、更新頻度が低く時系列の変動として使える粒度ではない。** 「今節は絞ってきた」といった短期変動は公開データからは追えない。→ **時系列特徴量としては棄却。** 静的なBMI・体格指標としてなら使えるが、それはほぼAかつ効果も薄い。
- **フレーム等の機材情報は一部媒体で公開されているが、体系的な履歴データベースが存在せず、収集コストに対して見返りが薄い。**
- **ギア倍数だけが唯一、数値で公開・履歴化可能な「機材変更」情報**である。→ C-2'に統合済み。

**結論**：C-4は独立候補としては閉じる。工数はC-1・C-5に回す。

### C-5. 競走得点の陳腐化ラグ 【新規追加・最優先級】

**なぜCか**：競走得点は一定期間の平均で算出され、**成績が級班や表示得点に反映されるまでにタイムラグがある**（級班改編は年2回、1月と7月）。つまり「実力が上昇中の選手」「下降中の選手」は、表示得点が真の実力とズレたまま出走している。**市場は出走表の表示得点を見て賭ける**ため、このズレはそのままオッズの歪みになる。

しかも重要なのは、**表示得点は対戦相手の強さを補正していない**という点。同じ得点でも、強い相手に揉まれて取った得点と弱い相手から取った得点は価値が違う。楽天Kドリームスの「Kレーティング」が対戦相手補正の思想を採用しているが、これを自前で構築し**表示得点との差分（residual）**を特徴量にすれば、「市場が見ている粗い指標」と「精密指標」の乖離を直接ベットできる。これは C の定義に最も忠実な候補。

**実装する特徴量**：

```
elo_rating                  # 自前構築。1走ごとに対戦相手のレーティング差に応じて更新
                            # 初期値は級班別の平均、K値はグリッドサーチ
elo_minus_displayed_score_z # ★本命特徴量：eloのz-score − 表示競走得点のz-score
                            # 正＝市場が過小評価、負＝過大評価
elo_trend_30d               # 直近30日のelo変化量（上昇/下降トレンド）
elo_trend_90d
days_since_grade_revision   # 級班改編からの経過日数（ラグが大きいほど乖離が開くはず）
elo_residual × days_since_grade_revision  # 交互作用：改編直前ほど乖離が大きいという仮説
```

**測定方法**：`elo_minus_displayed_score_z` を五分位に分割し、各分位で 比＝実測連対率÷市場含意確率 を算出。単調増加が出れば、市場が表示得点に引きずられていることの直接的な証拠になる。**この単調性はTRAIN/TESTで極めて安定するはず**（構造的な要因なので）。

### C-6. 級班ボーダー距離によるインセンティブ非対称 【新規追加・推奨】

**なぜCか**：級班の定期入替は年2回（1月・7月）で、**前期（1〜6月）／後期（7〜12月）の成績で決まる**。評価点は「平均競走得点 − 失格点」で計算され、失格1回につき3点減点される。つまり**期末が近づくほど、ボーダー際の選手は昇級/降級がかかった走りをする**。市場でも「気合が入る」程度には語られているが、**ボーダーまでの点差を数値化して確率補正している者はいない。**

**実装する特徴量**：

```
days_to_period_end          # 期末（6/30, 12/31）までの残日数
score_minus_border          # 現在の評価点 − 該当級班の昇級/降級ボーダー
                            # ボーダー値は期ごとに公表されるので外部マスタが必要（軽量）
is_border_zone              # |score_minus_border| < 閾値（1.0点など）
border_pressure             # is_border_zone × (1 / days_to_period_end)
                            # 期末が近くボーダー際 ＝ 最大圧力
border_pressure × 昇級側/降格側  # 昇級狙い（積極的に前へ）と降格回避（堅実に）で
                                 # 行動が非対称になるはずなので符号を分ける
failure_points_accumulated  # 累積失格点（3点/回）
```

**仮説**：昇級圏ギリギリの選手は期末に積極的な走りをする＝先行・捲りの発生率が上がり、結果として決まり手分布が変わる。降格圏の選手も同様。**この効果は「選手の強さ」ではなく「動機」の変数**であり、既存の強さ系特徴量とは直交する可能性が高い＝モデルへの純増寄与が期待できる。

**必要な外部データ**：期別の昇級/降格ボーダー点（公表値）。年2回×級班数の小さなマスタで済む。

### C-7. 上がりタイムの履歴化 【⚠️ 大部分が既に本番実装・採用済み（2026-07-30 確認）】

**現状**：`wt_entries.final_half`（充填率96.3%）から、以下が **2026-07-18 に本番採用済み**
（`SB_DYN_COLS_WT`・[[keirin_sb_dynamics_pipeline]]）:

- `fh_rel_90` … 直近90日の上がり相対値平均（**自上がり − レース中央値**・負=速い）
- `fh_best_rate_90` … 直近90日の「レース内上がり最速」率

A/B検証（2独立窓×5seed）で ΔAUC +0.013/+0.011・指数1位3着内率 +0.93pt/+1.10pt・
重要度2〜9位/48 で採用。**本メモが「注意」として挙げた「必ずレース内z-scoreに
正規化すること」は既に実装で守られている**（レース中央値との差分を取っている）。

→ **新規性が残るのは `agari_rank_minus_finish_rank`（上がり順位 − 着順）のみ。**
優先度を下げ、他候補の測定に相乗りさせる形で1回測ればよい。

### C-7（原文・記録として保持）

**なぜCか**：上がりタイム（最終200mのタイム）はレース結果データに含まれる公開情報だが、**着順ほどには見られていない**。着順は展開に左右されるが、上がりタイムは脚力の直接指標に近い。「着順は悪いが上がりタイムは優秀」＝展開に恵まれなかっただけの選手を検出でき、これは市場が織り込みにくい。

```
agari_time_last             # 前走の上がりタイム
agari_time_z_in_race_last   # 前走のレース内相対z-score（バンク・風の条件を吸収）
agari_time_best_90d
agari_rank_minus_finish_rank # ★上がりタイム順位 − 着順　正＝展開に恵まれなかった
                             # ＝「次走で見直せる」候補の検出
```

**注意**：上がりタイムはバンク周長・当日の風・レース展開（スローかハイペースか）に強く依存するため、**絶対値でなく必ず同レース内のz-scoreに正規化してから使うこと。** 生の秒数をそのまま入れると会場効果を拾って壊れる。

## 4. 測定プロトコル（全候補共通）

新しい特徴量を作ったら、モデルに入れる前に必ず以下を通す。**モデルに入れてから精度で判断してはいけない**（他の特徴量と交絡して判定不能になるため）。

### ステップ1：比の算出（30分で判定）

```
比 = 実測連対率（または的中率） ÷ 市場の含意確率
```

- 市場の含意確率は確定オッズから算出（控除率25%を戻して正規化すること。生のオッズ逆数の合計は1.333になるので必ず1.0に正規化する）
- 候補特徴量を**五分位（またはフラグなら2群）**に分割し、各セグメントで比を算出
- **比が1.00付近なら織り込み済み＝その特徴量は捨てる。ここで即座に打ち切ること。**

### ステップ2：閾値判定

- **比 > 1.333 でなければROI 100%には届かない**（0.75 × 1.333 = 1.0）
- 比が1.0〜1.333の範囲で有意でも、それは「損失を小さくする」効果しかない
- ただし**比 < 1.0 が有意なセグメントは「除外ルール」として価値がある**（買い目から外すことで全体の期待値が上がる）。上振れだけでなく下振れも記録すること

### ステップ3：TRAIN/TEST両窓での符号・幅の一致

- 両窓で**符号が一致し、かつ幅（効果量）が同オーダー**であることを要求
- 片窓のみで有意なものは多重比較ノイズとして棄却
- 検定した仮説の総数を記録し、Bonferroni または BH法での補正後p値も併記すること

### 追加の必須チェック（見落としやすい）

4. **セグメントの最小サンプルサイズ**：各分位で最低でも数百件のレースがないと比の信頼区間が広すぎて判定不能。サンプル数と信頼区間を必ず併記する
5. **交絡の確認**：新特徴量が既存特徴量（特に競走得点・人気順位）とどの程度相関しているかを確認。相関が高い場合、比の改善は既存特徴量の再発見にすぎない可能性がある。**人気順位帯で層別してもなお比が改善するか**を見ること
6. **時間的安定性**：TRAIN/TESTの2分割だけでなく、年次・期別（前期/後期）でも符号が反転しないか確認。級班改編（年2回）を跨ぐ構造変化に注意
7. **実行可能性**：その特徴量が**発走前に確定しているか**を確認。上がりタイムは前走のものなら可、当該レースのものは当然使用不可。ギア倍数は当日変更があるため、いつ時点の値を使うかを明示

### 実装仕様の確定事項（2026-07-30 追記・既存実装との整合のため必読）

8. **⚠️「連対率(2着以内)」と「3着内率」を混在させないこと**
   本プロトコルは「比 = 実測**連対率** ÷ 市場含意確率」と記載しているが、
   既存の全検証は **3着内・trio（三連複）基準**で構築されている。
   連対（2着以内）で測るなら市場側も `quinella` / `quinellaPlace` オッズから
   作り直す必要があり、混ぜると比が壊れる。
   利用可能な `wt_odds.bet_type` は trifecta / trio / quinellaPlace / exacta / quinella。
   **S7が三連複である以上、3着内・trio基準で統一すること。**

9. **市場含意確率の作り方（単一選手）と必須の検算**
   単一選手の市場3着内確率は、三連複35通りの市場確率から**周辺化**して得る
   （各車は35通り中15通りに出現）:
   ```
   market_P(車i が3着内) = Σ_{i を含む組} 正規化(0.75 / trio_odds)
   ```
   **検算: Σ_i market_P(i) = 3.0000 になること**（3着以内に必ず3車入るため）。
   実測で 3.0000（n=3,000サンプル）を確認済み。周辺化のバグはこの検算で一発で出る。
   ペア確率も同様に「そのペアを含む5通りの和」で得る。

10. **落車・失格は既存データで検出可能**（C-1の欠場明け分離・C-6の失格点に使用）
    `finish_order = 0` の **97.7% が `final_half` 非NULL** ＝ 出走して失格/落車。
    よって `finish_order = 0 AND final_half IS NOT NULL` で落車/失格を抽出できる。
    ただし「斡旋されていたのに出走表に載らない欠場」は斡旋データが無いため検出不可。

12. **⚠️【最重要】レース単位の区分は比が構造的に 1.000 に固定される**
    市場の周辺確率は Σ_i P_i = 3 に正規化され、実測も1レース必ず3車が3着内。
    よって**「レース全体を同じラベルに割り当てる区分」では分子と分母が恒等的に一致し、
    比は必ず 1.000（t = -0.00）になる**。実測でこれが発生して発覚した
    （C-6 期末までの日数・「今節未走×1日目」など）。

    → **市場のミスプライシングは【レース内の相対的な序列】にしか存在し得ず、
      レース全体の水準には原理的に存在しない**（オッズがレース内で正規化されるため）。

    **比で検証できない仮説（レース単位）**: 競輪場・バンク周長・グレード・開催日・
    期末までの日数・**気象（C-3 のほぼ全て）**・レースの荒れやすさ。
    これらは「配当分布の差」か「具体的な買い目戦略のROI差」で測るしかない。

    **比で検証できる仮説（レース内で選手を差別化するもの）**: 連戦負荷・elo残差・
    級班内位置・車番・脚質・ライン位置・same-meet form など。

    ⚠️ **C-3（気象）はこの制約に該当する。** 気象庁データを収集しても、
    「雨のレースは荒れる」を比では検証できない。収集前にこの点を認識すること
    （検証するなら「雨 × 脚質」のようにレース内で選手を差別化する形にする必要がある）。

11. **C-6 の実装上の障害**（着手前に認識しておくこと）
    - 評価点（平均競走得点 − 失格点）そのものが winticket データに存在しない
      → `race_point` の平均で近似する必要がある
    - 公式ボーダー点の外部マスタが必要
    - 期末（6/30・12/31）付近のレースに限るとサンプルが薄くなる
    → **代替案**: 公式ボーダーの代わりに「級班内での race_point パーセンタイル」を
      proxy にする（上位＝昇級圏際・下位＝降級圏際）。外部マスタ不要で実装できる。

## 5. 実行順序の推奨

外部収集ゼロで実装のみ、かつ事前期待が高い順に。

### 改訂版（2026-07-30・実データ確認を反映）

1. **C-1（連戦負荷・遠征距離）** — 真に未検証。緯度経度マスタのみで既存履歴から全計算可能
2. **C-5（得点の陳腐化ラグ）** — 外部データ不要。Elo実装のみ。理論的に最も筋が良い
   ※Elo単体は `exp_elo_linecoop_wt.py` / `exp_elo_monthly_wt.py` で検証済（AUC +0.003 だが
     7月のレース単位指標が悪化し不採用）。実装は `src/` に無く exp スクリプト内のみ。
     **ただし `elo − 表示得点` の residual を市場比で測る設計は未実施であり、そこが本命。**
     AUCで落ちた仮説が市場比で生きている可能性は十分ある（我々の精度が上がらなくても
     市場が織り込んでいなければ妙味になるため）
3. **C-6（級班ボーダー）** — 繰り上げ。ボーダーは級班内パーセンタイルで proxy 化（上記11）
4. **C-7 の残り（上がり順位 − 着順）** — 他候補の測定に相乗り。1回測って終了
5. **C-3（気象）** — 気象庁CSV取得＋アメダス地点マッピング＋バンク方位角マスタが必要。
   雨は「再検証」（G06で束として一度否定済み）、風は headwind 成分分解で一度だけ再検証して打ち切り

**閉じた候補**: C-2（前検日タイム＝通常競輪では非公開）/ C-4（機材・体重＝粒度不足）/
**C-2'（ギア変化量＝98.4%で不変・分散なし）**

### 実装単位の推奨

C-1・C-5・C-6・C-7残りはいずれも**外部収集不要**なので、**1本の測定スクリプトで
全特徴量を構築し、単一のデータロード・単一のオッズ走査で一括測定する**のが効率的
（オッズ走査が最も重いため、候補ごとにスクリプトを分けると4倍の時間がかかる）。
