# WEB品質監査スキル（Web Quality Audit）

## 概要

このスキルは、WEBシステムのプロジェクトに対して包括的な品質監査を実施する。9つの専門エージェントがそれぞれの観点で並列にチェックを行い、PMエージェントが結果を統合して優先度付きの監査レポートを生成する。ユーザーが修正対象を選択した後、修正を実施し、再度品質チェックを行うサイクルを回す。

## 全体フロー

```
1. 対象の特定と技術スタック検出
2. 各専門エージェントが並列でWebSearchにより最新基準を取得
3. 各専門エージェントが並列で品質チェック実施
4. PMエージェントが結果統合 → 監査レポート（マークダウン）生成
5. ユーザーに監査レポート提示、修正対象の選択を依頼
6. 選択された課題の修正を実施
7. 再チェック（選択項目のみ or 全項目）
8. 必要に応じてサイクルを繰り返す
```

## Step 1: 対象の特定と技術スタック自動検出

### 対象の特定

ユーザーに以下を確認する（AskUserQuestionを使用）：

- **チェック対象**: ソースコード（フォルダパス）、デプロイ済みサイト（URL）、設計ドキュメント、またはその組み合わせ
- **特に重視する観点**（任意）: 特定のエージェント観点を優先したい場合

### 技術スタック自動検出

ソースコードが対象の場合、まず技術スタックを自動検出する。これにより各エージェントのチェック精度が大幅に向上する。

以下のファイルを調査して技術スタックを特定する：

- `package.json` → フレームワーク（React, Vue, Next.js, Nuxt, Angular等）、依存ライブラリ
- `composer.json` / `Gemfile` / `requirements.txt` / `go.mod` / `pom.xml` / `build.gradle` → バックエンド言語・フレームワーク
- `Dockerfile` / `docker-compose.yml` → コンテナ構成
- `.github/workflows/` / `Jenkinsfile` / `.gitlab-ci.yml` → CI/CD構成
- `nginx.conf` / `apache.conf` / `Caddyfile` → Webサーバー構成
- `tsconfig.json` → TypeScript使用有無
- `.eslintrc` / `.prettierrc` → Lint/Formatter設定
- `next.config.js` / `nuxt.config.ts` / `vite.config.ts` → ビルドツール

検出結果を以下の形式で整理する：

```
【検出された技術スタック】
- フロントエンド: React 18 + TypeScript + Next.js 14
- バックエンド: Node.js + Express
- データベース: PostgreSQL（Prismaで接続）
- インフラ: Docker + nginx
- CI/CD: GitHub Actions
- テスト: Jest + React Testing Library
```

この情報を全エージェントに渡すことで、フレームワーク固有のベストプラクティスに基づいたチェックが可能になる。

## Step 2: 専門エージェントによる並列チェック

全9エージェントをAgentツールで並列起動する。各エージェントには以下を渡す：

- チェック対象のパス/URL
- 検出された技術スタック情報
- 対応するリファレンスファイルのパス（`references/` 配下）

### エージェント一覧

| # | エージェント | リファレンスファイル | 主な観点 |
|---|---|---|---|
| 1 | シニアエンジニア | `references/senior-engineer.md` | コード品質、設計パターン、保守性 |
| 2 | QA | `references/qa.md` | テスト網羅性、品質プロセス |
| 3 | 性能 | `references/performance.md` | パフォーマンス、最適化 |
| 4 | セキュリティ | `references/security.md` | 脆弱性、セキュリティ設計 |
| 5 | 法務 | `references/legal.md` | ライセンス、プライバシー、法的リスク |
| 6 | アクセシビリティ | `references/accessibility.md` | WCAG準拠、ユニバーサルデザイン |
| 7 | UX/UI | `references/ux-ui.md` | ユーザビリティ、一貫性 |
| 8 | インフラ/DevOps | `references/infrastructure.md` | デプロイ、監視、可用性 |
| 9 | SEO/Web標準 | `references/seo.md` | SEO、Web標準、構造化データ |

### 各エージェントの実行手順

各エージェントは以下の手順で動作する：

1. **最新基準の取得**: WebSearchで担当領域の最新ベストプラクティス・ガイドラインを検索し、チェック基準を更新する。検索クエリは技術スタックに応じて調整する（例：「React 18 performance best practices 2026」）
2. **リファレンスの読み込み**: `references/` 配下の対応ファイルを読み、チェック項目リストを取得する
3. **チェック実施**: ソースコード解析、サイト検査（デプロイ済みの場合）、ドキュメント確認を行う
4. **結果出力**: 以下の形式でJSON結果を返す

```json
{
  "agent": "エージェント名",
  "score": 75,
  "summary": "チェック概要（2-3文）",
  "issues": [
    {
      "id": "SEC-001",
      "severity": "Critical",
      "title": "課題タイトル",
      "description": "課題の詳細説明",
      "location": "ファイルパスまたはURL",
      "recommendation": "推奨される修正方法",
      "reference": "参考URL（WebSearchで取得した最新情報）"
    }
  ]
}
```

### エージェント起動のプロンプトテンプレート

各エージェントを起動する際は、以下のテンプレートに沿ってプロンプトを構成する：

```
あなたは「{エージェント名}」の専門家です。WEBシステムの品質監査を担当します。

【技術スタック】
{検出された技術スタック情報}

【チェック対象】
{ソースコードパス / URL / ドキュメントパス}

【実行手順】
1. まずWebSearchで以下を検索し、最新のベストプラクティスを取得してください：
   {技術スタックに応じた検索クエリ例}

2. 次に以下のリファレンスファイルを読んでください：
   {リファレンスファイルパス}

3. リファレンスと最新情報を基に、対象のチェックを実施してください。

4. 結果を以下のJSON形式で出力してください：
   - agent: "{エージェント名}"
   - score: 0-100のスコア
   - summary: チェック概要
   - issues: 検出された課題の配列（各課題にid, severity, title, description, location, recommendation, referenceを含む）

【重大度の基準】
- Critical: システム停止、データ漏洩、法令違反に直結する問題
- High: 主要機能の不具合、重大なパフォーマンス劣化、セキュリティリスク
- Medium: ユーザー体験の低下、保守性の問題、軽微なリスク
- Low: コーディング規約違反、改善推奨事項、ベストプラクティスからの逸脱
- Info: 参考情報、将来的な改善提案

【スコア基準】
- 90-100: 優秀。重大な問題なし、ベストプラクティスに準拠
- 70-89: 良好。軽微な改善点あり
- 50-69: 要改善。対応すべき課題が複数存在
- 30-49: 問題あり。重要な課題への対応が必要
- 0-29: 深刻。早急な対応が必要
```

## Step 3: PMエージェントによる統合と監査レポート生成

全エージェントの結果が揃ったら、PMエージェントとして結果を統合する（これはメインの処理フローで行う。別エージェントの起動は不要）。

### 統合処理

1. **全課題の収集**: 各エージェントが報告した課題を一つのリストに統合
2. **重複排除**: 複数エージェントが同じ箇所を指摘している場合、統合して最も高い重大度を採用
3. **優先度決定**: 以下の基準で改善の優先度を決定
   - 重大度（Critical > High > Medium > Low > Info）
   - 影響範囲（広範囲に影響 > 局所的）
   - 修正コスト（低コスト > 高コスト、同じ重大度なら低コストを優先）
4. **総合スコア算出**: 各エージェントのスコアの加重平均（デフォルトは均等配分）

### 監査レポートの出力先

レポートはプロジェクトルート直下の `quality_reports/` フォルダに保存する。
- フォルダが存在しない場合は自動作成する
- ファイル名: `audit-report-YYYYMMDD.md`（YYYYMMDDは実行日）
  - 例: `audit-report-20260331.md`
- 同日に複数回実行する場合: `audit-report-YYYYMMDD-2.md`, `audit-report-YYYYMMDD-3.md`
- 再チェック結果: `audit-report-YYYYMMDD-recheck.md`

### 監査レポートの構成

以下のテンプレートに従ってマークダウンファイルを生成する。
テンプレートは `references/report-template.md` を参照。

レポートは以下のセクションで構成される：

```markdown
# WEB品質監査レポート

## 監査概要
- 対象、実施日時、技術スタック

## 総合スコア
- 全体スコアと各カテゴリスコアの一覧表

## カテゴリ別サマリー
- 各エージェントの概要とスコア

## 課題一覧（優先度順）
- 全課題を優先度順に一覧表示
- ID、重大度、カテゴリ、タイトル、概要、推奨対応

## 詳細分析
- カテゴリごとの詳細な分析結果
```

## Step 4: ユーザーへの提示と修正対象の選択

1. 生成した監査レポートをユーザーに提示する
2. AskUserQuestionで修正対象の選択を依頼する：
   - 課題IDを指定して個別選択
   - 重大度レベルでの一括選択（例：Critical と High のみ）
   - 全課題を対象とする選択
   - 修正不要（レポートの確認のみ）

## Step 5: 修正の実施

ユーザーが選択した課題について修正を実施する：

1. 各課題の推奨対応に基づき、ソースコードを修正
2. 修正が複数ファイルにまたがる場合は、関連性の高いものをまとめて実施
3. 修正内容をユーザーに説明し、確認を得る
4. 修正完了後、変更の差分サマリーを提示

## Step 6: 再チェック

修正完了後、再度品質チェックを実施する：

- **選択項目のみ再チェック**（デフォルト）: 修正した課題に関連するエージェントのみ再起動
- **全項目再チェック**: ユーザーが要求した場合、全エージェントを再起動

再チェック結果は、前回の監査レポートと比較する形で提示する：
- スコアの変動（↑↓）
- 解決済み課題の一覧
- 新たに検出された課題（修正に伴い発生した問題）
- 残存する課題

## 重大度の定義

| レベル | 定義 | 対応目安 |
|--------|------|----------|
| **Critical** | システム停止、データ漏洩、法令違反に直結。ユーザーへの直接的な被害が発生する、または発生する危険性が極めて高い | 即時対応必須 |
| **High** | 主要機能の不具合、重大なパフォーマンス劣化、セキュリティリスク。サービス品質に大きな影響を与える | 1週間以内に対応 |
| **Medium** | ユーザー体験の低下、保守性の問題、軽微なリスク。現時点では大きな影響はないが放置すると問題が拡大する可能性がある | 次回リリースまでに対応 |
| **Low** | コーディング規約違反、改善推奨事項、ベストプラクティスからの逸脱。品質向上のために対応が望ましい | 余裕がある時に対応 |
| **Info** | 参考情報、将来的な改善提案。対応は任意だが知っておくと有益 | 対応任意 |

## 注意事項

- 各エージェントは必ずWebSearchで最新のベストプラクティスを取得してからチェックを行う。これは技術の進歩が速いため、古い基準でチェックすることを防ぐため
- 技術スタックの自動検出結果は、エージェントが検索クエリを構成する際の精度に直結する。必ず最初に実行すること
- デプロイ済みサイトが対象の場合、実際のページアクセスはCodex in Chrome（利用可能な場合）またはWebFetchを使用する
- 監査レポートはマークダウン形式で、プロジェクトルート直下の `quality_reports/` フォルダに保存する
- フォルダが存在しない場合は自動作成する
- ファイル名には実行日の年月日を含める: `audit-report-YYYYMMDD.md`（例: `audit-report-20260331.md`）
- 同日に複数回実行した場合はサフィックスを付与: `audit-report-YYYYMMDD-2.md`
- 再チェック結果は `audit-report-YYYYMMDD-recheck.md` とする
