## 1. データ源の全体像

「スクレイピング」と一括りにされがちだが、chihou には**性質の違う3系統**がある。
壊れ方も回収方法も別なので、まず分けて考える。

| 系統 | 取得元 | 格納先 | 取得方式 | 実行場所 |
|---|---|---|---|---|
| **A. 本体データ** | UmaConn SDK（NVDTLab.dll） | `chihou.races` / `race_entries` / `race_results` / `race_payouts` / `horses` | COM（スクレイピングではない） | Windows VM `umaconn_agent.py` |
| **B. オッズ時系列** | UmaConn SDK（速報） | `chihou.odds_history` | COM ポーリング | 同上（realtime モード） |
| **C. 外部指数** | netkeiba / 吉馬 の**Webスクレイピング** | `sekito.netkeiba` / `sekito.kichiuma` | HTTP スクレイプ | **sekito リポジトリ**（`backend/scripts/bin/scrape/*`）・VPS |

- **C は kiseki リポジトリの管轄外**。壊れているときの修理は `~/GitHub/sekito` 側で行う。
- `sekito.anagusa`（穴ぐさ）は**中央専用**で、地方場のレコードは 0 件。地方の特徴量には
  一切入っていない（CLAUDE.md の記述どおり）。
- 取得の成否は `sekito.data_fetch_status`（date × course × race × data_type）に記録される。
  **C 系統の障害診断はまずこのテーブルを見ること**（4.4 節）。

### モデルが実際に使っている外部データは 2 列だけ

44特徴のうち外部指数由来は 5 本（`kc_sp_z` / `nk_idx_z` / `kc_rank_n` / `nk_rank_n` /
`ext_missing`）で、その入力は

- `sekito.kichiuma.sp_score`
- `sekito.netkeiba.idx_ave`（**`is_time_index = true` の行に限定**）

の 2 列のみ。`sp_trust` / `sp_adjust` / `sp_max` / `sueashi` / `senko`、netkeiba の
`idx_max` / `idx_distance` / `idx_course` / `p_rank` / `sire` などは**取得済みだが未使用**。
学習側 `train_chihou_prod_lgb.add_external_features` と serve 側

### 3.5 🔴 複勝バックテストの上方バイアス（実証済み）

`place_odds` の欠損は**ランダムではなく着順と強く相関している**。
HR 払戻（`race_payouts`）由来の補完は**1〜3着馬にしか値を与えない**ためである。

`place_odds` 充足率（ばんえい除く・完走馬）:

| 期間 | 1-3着 | 4着以下 |
|---|---|---|
| 2024-01 〜 2025-12 | 0.4% | 0.0% |
| **2026-01 〜 2026-03** | **98.3%** | **0.0%** |
| 2026-04 〜 | 99.8% | 93.3% |

一方、複勝 ROI を計算している 3 スクリプトはいずれも
**`place_odds` が NULL の行を黙って落としてから ROI を出している**:

- `scripts/chihou_rebuild_walkforward.py:309` — `valid = sub[sub["place_odds"].notna()]`
- `scripts/backtest_chihou_sweetspot.py:80` — 同上
- `scripts/aggregate_chihou_recent.py:176` — 同上

**2026-01〜03 の期間では、この絞り込みが「4着以下の馬を全て捨てて 1〜3着馬だけ残す」
操作と等価になる。** すなわち母集団 `valid` の的中率が定義上ほぼ 100% になり、
`ROI = Σ(的中馬の複勝オッズ) / len(valid)` は**複勝オッズの平均値そのもの（2〜5倍）**に
なる。2024-10〜2025-12 の行はほぼ全て捨てられ、残るのはこの偏った 3 か月と
クリーンな 2026-04 以降だけ。

> **したがって「place_bet 複勝ROI 0.972」「複勝ROI 1.046」等、
> `place_odds` を使って算出された既存の数値はすべて信頼できない。**
> P5 で **2026-04 以降のみ**を母集団として再計算すること
> （それでも 4 か月・n は大幅に減る）。
> 併せて 3 スクリプトに「`place_odds` 欠損率が着順帯で偏っていたら中断する」
> ガードを入れること。落として黙って進むのが事故の直接原因である。

**バイアスの大きさ（実測）**: 2026-01〜03 の完走馬全体（ばんえい除く）で
旧コードと同じ計算をすると:

| 指標 | 値 |
|---|---|
| `place_odds.notna()` 後の母集団 | 8,579 行 |
| そのうち 1〜3着 | **8,579 行（100.0%）** |
| naive 複勝ROI | **2.440** |
| レース単位で全馬揃っているレース | **0 / 2,910** |

的中率が定義上 100%、ROI は複勝オッズの平均そのもの。**この期間の複勝 ROI は
数値としての意味を持たない。**

**対応（本ブランチで実施済み）**: `src/services/chihou_place_odds_guard.py` を新設し、
**レース単位で全出走馬の複勝オッズが揃っているレースだけ**を ROI の母集団にする。
期間で切るのではなく充足そのものを見るので、データが増えれば自動的に対象が広がる。
`chihou_rebuild_walkforward.py` / `backtest_chihou_sweetspot.py` /
`aggregate_chihou_recent.py` の 3 本に適用し、監査結果（着順帯別の充足率と
落としたレース数）を必ず出力するようにした。

⚠️ **払戻を 2024 年まで遡ると、この壊れ方が 2024〜2025 にも広がる**
（HR は 1〜3着しか持たないため同じ形の欠損が作られる）。
**バックフィルの前に本ガードを入れること**が必須。

`chihou.odds_history`（2026-04-07 〜）から発走前最終スナップを引けば全馬の複勝オッズが
取れるので、**2026-04 以降については `place_odds` の NULL を埋めきることが可能**
（`backfill_chihou_place_odds.py` が既にその実装）。それ以前は**恒久的に回復不能**。

### 4.2 netkeiba — 二重の問題

**(a) タイム指数はそもそも 2025-06 からしか無い**

モデルが使う `nk_idx` は `is_time_index = true` の行に限定されるが、
`is_time_index` が立った行が出るのは **2025-05（部分・620行）→ 2025-06（本格・12,232行）** から。
**2024-01 〜 2025-04 は `is_time_index` が 1 行も無い＝ nk_idx は全件 NULL。**

主要クエリ:

```sql
-- 月次カバレッジ
SELECT substr(date,1,6) ym, count(*) races, count(DISTINCT date) days,
       count(DISTINCT course) venues
FROM chihou.races GROUP BY 1 ORDER BY 1;

-- 結果の取得抜け（未来・ばんえい除く）
SELECT r.date, count(*) missing, count(DISTINCT r.course) venues
FROM chihou.races r
LEFT JOIN (SELECT DISTINCT race_id FROM chihou.race_results) s ON s.race_id = r.id
WHERE s.race_id IS NULL AND r.date >= '20240101'
  AND r.date < to_char(now(),'YYYYMMDD')
GROUP BY 1 ORDER BY 1;

-- 外部指数の供給率（出走馬単位・月次）
WITH base AS (
  SELECT r.date, re.horse_number, rc.code cc, r.race_number
  FROM chihou.races r
  JOIN chihou.race_entries re ON re.race_id = r.id
  JOIN sekito.racecourse rc ON rc.netkeiba_id = r.course
  WHERE r.date >= '20240101' AND r.course <> '83'
)
SELECT substr(b.date,1,6) ym, count(*) entries,
  round(100.0*count(*) FILTER (WHERE nk.is_time_index)/count(*),1) nk_time_pct,
  round(100.0*count(kc.horse_no)/count(*),1) kc_pct
FROM base b
LEFT JOIN sekito.netkeiba nk ON nk.course_code=b.cc
  AND nk.date=to_date(b.date,'YYYYMMDD')
  AND nk.race_no=b.race_number AND nk.horse_no=b.horse_number
LEFT JOIN sekito.kichiuma kc ON kc.course_code=b.cc
  AND kc.date=to_date(b.date,'YYYYMMDD')
  AND kc.race_no=b.race_number AND kc.horse_no=b.horse_number
GROUP BY 1 ORDER BY 1;

-- スクレイパーの死活（sekito 側）
SELECT to_char(date,'YYYY-MM') ym, data_type, fetch_status, count(*)
FROM sekito.data_fetch_status
WHERE course_code LIKE 'N%' AND date >= '2026-04-01'
GROUP BY 1,2,3 ORDER BY 1,2,3;

-- 指数の算出時刻 vs レース日
SELECT r.date, min(ci.calculated_at) t0, max(ci.calculated_at) t1, count(*) rows
FROM chihou.calculated_indices ci JOIN chihou.races r ON r.id = ci.race_id
WHERE ci.version = 13 AND r.date >= to_char(now()-interval '14 days','YYYYMMDD')
GROUP BY 1 ORDER BY 1;
```

## 10. 目標の再設定と、それに対する最大の障害（2026-08-13）

### 10.1 目標

> レース内で**不人気の激走馬**を探す指数を作り、**1レースに1〜2頭**ピックアップする。
> 人気馬でも3着以内に入れなさそうなら**無理に推奨しない**。入着可能な場合のみ推奨する。

評価軸は **A: 複勝的中率（3着以内に入る率）を主軸**、B: 複勝ROI は参考値。
理由は 2 章のとおり、`finish_position` は 2024-01 以降の全期間あるが
`place_odds` は 2026-04 以降しか無く、ROI を主軸にすると検証窓が 4 か月に潰れるため。

### 10.2 これは既に本番に載っている（`chihou_is_place_pick`）

`backend/docs/chihou_darkhorse_feasibility_2026_08_05.md` で確立済み:

> 発走前**6番人気以下** ∧ 指数**3位以内** ∧ 市場上位3頭シェア**<0.63** ∧ **8頭立て以上**
> → 複勝圏率 **51.5%**（母集団 11.79% の **4.36倍**・p=1.0e-22）

同文書は「単勝はエッジなし」「複勝ROIの主張は確定オッズによる look-ahead で崩れた」と
訂正済みで、**生き残っているのは的中率の条件だけ**。今回の目標と完全に一致する。

### 10.3 🔴 51.5% は look-ahead で、到達不能な数字だった

**検証に使われた walk-forward 指数は `ALL_FEATURES`（市場特徴5本）で学習・予測しており、
その入力は `race_results.win_odds` / `win_popularity` ＝ 確定オッズ**
（`chihou_darkhorse_wf_build.py` → `add_market_features`）。
一方 **条件側（人気順位・シェア）は発走前オッズ**から作っている。

この**入力の食い違いが look-ahead を生む**。同一スクリプトで3通りの指数を作って確かめた
（`--no-market` / `--prerace-lead 5` を新設）。

**指数1位馬の勝率（walk-forward・重なる2四半期）**

| 四半期 | 確定オッズ | 発走5分前オッズ | 市場なし（＝本番） |
|---|---|---|---|
| 2026Q2 | 45.8% | **44.1%** | 39.9% |
| 2026-07 | 42.1% | **41.6%** | 36.7% |

素の順位精度で見れば、確定オッズと発走前オッズの差は 0.4〜1.7pt しかない。
「オッズを見せること」自体の価値は本物で、見せないと 5〜6pt 落ちる。

**ところが穴馬条件に適用すると話が逆転する**（discovery・発走前6番人気以下・母集団 11.8%）:

| 指数 | 全レース × 指数3位内 | シェア<0.63 × 指数3位内 |
|---|---|---|
| 確定オッズ | 43.2% (n=192) | **50.7%** (×4.28, n=71) |
| **発走5分前オッズ** | **— (n=2)** | **— (n=0)** |
| 市場なし（本番） | 26.1% (n=720) | **28.3%** (×2.39, n=212) |

**発走前オッズを入れると条件が空になる**。指数が市場と同じものを見れば、
市場が嫌っている馬を上位3位に置かなくなるからで、これは当然の挙動。

### 10.3.1 では確定オッズ版が選んでいた 186 頭は何だったのか

`wf_market.csv` の該当馬を発走5分前オッズと突き合わせた（2026-04-07〜06-30）:

| | 選ばれた 186頭 | 母集団 15,415頭 |
|---|---|---|
| 発走5分前オッズ 中央値 | **17.1倍** | 42.3倍 |
| 確定オッズ 中央値 | **7.2倍** | 64.1倍 |
| pre/final 比 中央値 | **2.30**（人気化） | 0.67（人気落ち） |
| 3着内率 | 42.5% | 12.0% |

**確定オッズでの人気順位: 1番人気7 / 2番人気45 / 3番人気110 / 4番人気22 / 5位以下2**
→ **186頭中162頭（87%）が最終的に1〜3番人気**。

つまりこの条件は「発走5分前は6番人気以下だが、締切までに2〜3番人気まで買われた馬」を
拾っていた。**締切後にしか分からない情報**であり、賭け時点では再現できない。

### 10.4 結論: 本番の作りは正しく、期待値だけが間違っていた

- **本番＝「オッズを見ない指数」+「発走前オッズによる絞り込み」は、この目的に対して
  アーキテクチャとして正しい。** 指数に市場を見せると穴馬を推せなくなる
- **直すべきは実装ではなく期待値**。この条件の honest な実力は
  **複勝圏率 約28%（母集団 11.8% の ×2.4）** であって 51.5% ではない
- 先行文書（`chihou_darkhorse_feasibility_2026_08_05.md`）は**条件側の look-ahead は
  訂正したが、指数側の look-ahead は見落としていた**。51.5% の記述は要訂正
- ⚠️ **5.4 節の「市場特徴がライブで無効」は、この目的においては欠陥ではない。**
  ただし「指数1位馬の勝率」のような一般的な順位精度では依然 5〜6pt 損しており、
  用途によって評価が割れる。**穴馬用と本命用で指数を分ける**設計が筋

## 12. 穴馬用と本命用で指数を分けるべきか（2026-08-13）

### 12.1 やったこと

「穴馬専用に学習した指数」が「汎用の市場なし指数」より穴馬を当てられるかを試した。
`train_binary_control` に `sample_weight` を追加し、`chihou_darkhorse_wf_build.py` に
`--upset-weight / --upset-from` を新設して 3 通りを walk-forward で作った。

- **plain**: 市場なし・重みなし（現行相当）
- **upset3**: 市場なし・確定4番人気以下を **x3**（対象 70.7%）
- **upset6**: 市場なし・確定6番人気以下を **x5**（対象 51.1%）

重み付けの基準は確定人気順位だが、**人気は特徴量に入れない**ので serve 時に人気を
知る必要はなく look-ahead にならない（学習集合の層別であって入力ではない）。

### 12.2 結果 — 有意な改善は無い

DISCOVERY・6番人気以下・シェア<0.63・8頭以上・最大2頭の複勝率:

| ルール | plain | upset3 | upset6 | n |
|---|---|---|---|---|
| 指数2位内 | 25.7% | **31.4%** | **30.5%** | ~110 |
| 指数3位内 | **29.4%** | 28.2% | 26.8% | ~220 |
| 指数4位内 | **27.7%** | 26.9% | 27.0% | ~390 |
| 指数5位内 | **28.2%** | 26.4% | 26.9% | ~570 |
| 指数6位内 | **25.9%** | 24.4% | 25.0% | ~770 |

- **指数2位内だけ両変種が +4.8〜5.7pt 改善**するが、n≈110 で SE≈4.3pt。単独では 1.2σ 程度
- **それ以外の全セルでは重み付けが僅かに悪化**する。符号が一貫しない
- 2変種が一致しているのは独立な証拠ではない（同じデータ・似たモデル）

### 12.3 より重要な構造的制約

穴馬の評価に使える窓は `odds_history` の都合で **2026-04-07 以降・2,894レースだけ**。
セルの n は 100〜600 で、**5〜8pt 未満の差は原理的に解像できない**。

> **いま穴馬モデルのチューニングは検証不能である。**
> どんな学習上の工夫をしても「効いたかどうか」を判定できない。

### 12.4 結論: 分けるのは「学習」ではなく「配信」

| 用途 | 指数 | 市場を見るか | 状態 |
|---|---|---|---|
| **穴馬** | 市場なしモデル + 発走前オッズで絞り込み | **見ない**（見せると条件が空になる・10.3） | ✅ 現行が正しい |
| **本命** | 市場ありモデル | **見る**（見せないと順位精度 5〜6pt 損・10.3） | ❌ 未実装（serve時にオッズを渡していない） |

- **穴馬専用モデルは作らない**。効果が測れないうちに複雑さだけ増える
- **分離は配信側で行う**。同じ学習系から2つの出力を出し、
  穴馬用は `odds_map` なし、本命用は `odds_map` あり で算出する
- 本命用にオッズを渡すには **発走直前の再算出経路**が要る（9.4）。
  毎分動いている `chihou_odds_decision_trigger.sh` に相乗りするのが自然

### 12.5 保留にした仮説（データが貯まったら再検証）

> **穴馬重み付け × 指数2位内** は plain 比 +5pt 前後。
> 事前登録して、前向きデータが 1 年ぶん貯まってから一度きりで検証する。
> いま採用してはいけない（多重比較の中の 1 セルにすぎない）。

## 13. 🔴 本番モデルは「市場込みで学習・市場なしで配信」されている（2026-08-14）

### 13.1 見落としていた区別

10〜12章では「市場を見る/見ない」を2値で扱っていたが、実際には**3通り**ある。

| | 学習 | 配信 | 実体 |
|---|---|---|---|
| ① | 市場込み(44) | 市場込み | 検証で使っていた条件（確定オッズ＝look-ahead） |
| ② | **市場込み(44)** | **市場なし** | **本番これ**。`odds_map` が渡されないため |
| ③ | 市場なし(39) | 市場なし | walk-forward の `--no-market` |

**②は「モデルが頼りにしている5本の特徴が、配信時には常に定数」という状態**で、

    odds_rank_n = 0.5 / speed_mkt_gap = clip(0.5 - speed_rank_n)
    kc_mkt_gap = clip(0.5 - kc_rank_n) / is_heavy_fav = 0

### 14.4b 🔴 バックフィルだけでは当日・翌日のレースが埋まらない（実際に踏んだ）

バックフィル直後の実測:

```
20260813  45レース  v14 45
20260814  34レース  v14  0   ← 当日
20260815  20レース  v14  0   ← 翌日
```

**API は `version = CHIHOU_COMPOSITE_VERSION` の行しか読まない**ため、
この状態では**当日のレースの指数が画面に一切出ない**。

原因は `inference_chihou_v14.py` の抽出条件 `AND r.head_count >= 6`。
`head_count` はレース後にしか入らないので（8.x 節と同じ罠）、
**未実施のレースは構造的にバックフィルの対象外**になる。

通常運用では cron の `calculate` が当日分を書くので問題にならないが、
**版を上げた直後だけは「前夜の cron は旧版で計算済み・バックフィルは未実施分を拾わない」
という穴が空く**。今回はデプロイが 06:23 JST で、前夜 22:00 の cron は v13 だった。

**対処（実施済み）**: 本番の calculate を直接叩いて埋めた。

```bash
ssh sekito "API_KEY=\$(grep '^CHANGE_NOTIFY_API_KEY=' ~/GitHub/kiseki/.env | cut -d= -f2-)
  curl -s -X POST 'http://127.0.0.1:8003/api/import/chihou/calculate?date=YYYYMMDD' \
       -H \"X-API-Key: \$API_KEY\""
```

> ⚠️ **版を上げるときの手順に「当日・翌日の calculate を叩く」を必ず含めること。**
> デプロイ → バックフィル → **当日/翌日の calculate** の3段。

### 8.6 死活監視の穴を塞いだ（**実施済み**）

netkeiba の縮退を `chihou_data_health_check.py` が**一度も検知していなかった**理由は 2 つ。

1. **供給元を OR で合算していた** — `kichiuma OR netkeiba` を 1 本の供給率にしていたため、
   kichiuma が健全なら netkeiba が全滅しても 95% を維持する
2. **判定が baseline 比のみ** — 段階的に崩れると baseline も一緒に下がるので比率が 1.0 に
   張り付き、**崩れきった後は永久に OK を返す**

本番実測がそれを示している:

```
[OK  ] 外部指数供給率 netkeiba(time_idx): 直近  6.5% (baseline 5.6%, 比率117.5%)
[WARN] 外部指数 取得日数 netkeiba(time_idx): 1/8 日 (12.5%  閾値 80%)
```

**対応（本ブランチで実施済み）**:
- 供給率を**供給元ごとに独立判定**。netkeiba は `is_time_index = true` に限定
  （モデルの入力条件と揃える。生の行数では使えないデータを数えてしまう）
- `check_external_index_active_days` を新設。**開催日のうちデータがある日の割合**を見るので、
  比率ベースが取りこぼす「日次 → 週1」の縮退を捕まえる（閾値 80%）
- スタブカーソルによる判定ロジックのテスト 8 件を追加
