# 予想フロー再設計計画（中央・地方）— 2026-11-06

ユーザーが示した目標フロー（下記）に対して、現状の設計を見直し、UI/UX の改善を含めて段階的な改修計画を立てる。
設計部（architect）・企画部（planner）・デザイン部（designer）の3つのレビューを統合したもの。
各レビューの全文は `docs/prediction_flow_review_2026_11_06/` にある。

```
公式データ → 入力検証
01 Core Analysis   : AS 基礎能力 / AAR 静的条件適性 → APS 条件適用後能力
02 Race Environment: Position Profile 脚質 / Track Bias 当日馬場 / Scenario 展開の発生確率
03 Race Simulation : LOCK → PEI 事前試行10万回 → 本番10万回 → 多段位置取り(START→中間→直線)
                     → 能力発揮の統合 → 着順確定・確率集計
04 Prediction      : PEI / 勝率・連対率・3着内率 / 馬券組合せ確率 → 予測保存・結果照合・Forward検証
```

## 0. 結論

- **現状は図のとおりではない。** 中央・地方とも、LightGBM が指数と勝率・複勝率を直接出す。
  シミュレーション、連対率、組合せ確率（馬連・ワイド・三連複）は配信されていない
- **図の「多段の位置取りシミュレータ」をそのまま作ることは勧めない。** 理由は2つ:
  1. データが足りない。中央の通過順は 1〜2コーナーが約半数しか無い（2024年以降の完走 177,074頭で
     `passing_1` 52.4%・`passing_2` 58.1%・`passing_3/4` 99.2%・2026-11-06 実測）。地方のラップは約26%（設計部の調査値・未再検証）
  2. 構造モデルは過去に LightGBM に負けている（v25 の乗数式で複勝率 −3.42pt。設計部の記載で、リポジトリ内の出典は未確認）
- **推奨は「既存の確率に合う能力分布を当てはめ、モンテカルロで着順を作る」形。**
  - v28 の単勝・複勝の確率に一致するように、馬ごとの平均 μ とばらつき σ を当てはめる
  - ばらつきを全馬で揃えると今の Harville 変換と同じになるので、現行を特別な場合として含む
  - 単勝と複勝の順位の食い違い（2026Q3 で 610R）を、連対率と組合せ確率へ矛盾なく渡せる
  - 図の 02（展開・馬場）は、後の段で「同じ脚質や内枠の馬をまとめて動かす要素」として足す
- **回収率は目的にしない**（控除率の壁・tier の廃止と同じ結論）。約束できるのは次の3つだけ:
  - 確率が互いに整合していること
  - proper scoring（対数損失）で改善すること
  - 発走前に固定した値で結果と照合できること

## 1. 見直しで見つかった本番の不具合（コードと本番 DB で確認済み）

### 1.1 🔴 中央の開催バイアス `meet_bias.py` がほぼ常に中立値になっている

`_extract_kai()`（`backend/src/indices/meet_bias.py:69`）は `jravan_race_id[8:10]` を返している。
ここは**場コード**で、開催回は `[10:12]`（docstring の例 `"2026032209011012" → kai="01"` とも合わない）。
検索パターン `f"{year}____{course}{kai}%%"` には「場コード＋場コード」が入るため、
**開催回の番号が偶然場コードと同じ開催（例: 1回札幌＝01/01）でしか先行レースを拾えない**。

- 🔴 **既存テストがこのバグを正解として固定している。** `backend/tests/test_meet_bias.py:80-84` は
  docstring が「第1回 (kai=01)」なのに `_extract_kai("2026040205010105") == "05"`（場コード）を期待している。
  Phase 4 で直すときはテストも書き換える
- 実測（2024年以降・`length(jravan_race_id)=16`）: 14,275R 中、回と場コードが一致するのは **840R（5.9%）だけ**。
  残りは常に中立値（設計部の別集計 9,973R 中 9,133R＝91.6% とも 840R で一致）
- 影響は1モジュールで終わらない。`frame_bias.py`（長期統計 70%＋開催バイアス 30%）と
  `pace.py` / `pace_handicap.py` も使っているので、**`frame_bias_index` と `pace_index` も
  ほぼ定数の成分で学習されている**
- また `Race.date < before_date` なので**当日の先行レースは使わない**。図の「当日馬場傾向」とは元々別物
- **その場で直さない。** 現行の v28 はこの壊れた値で学習済みなので、配信側だけ直すと学習時と配信時の入力がずれる。
  直すのは Phase 4 で、サブ指数の全期間再計算 → 再学習 → デプロイ・バックフィル・当日算出の3段と一組にする

### 1.2 🔴 地方の勝率・複勝率がレース内で正規化されていない

`chihou_calculator.py:837-841` は、較正済みヘッドの生の値を 0〜1 にクリップしただけで保存している。
**複勝確率は Harville 換算ではなく is_top3 ヘッドの値そのまま**（Harville は較正ヘッドが無いときの代替経路だけ）。

- 2026-10 実測: 勝率の合計は p10〜p90 で 0.70〜1.38、複勝率の合計は 2.51〜3.66
- 激走（`chihou_gekisou`）は自前でレース内の合計を 3 に正規化しているので影響を受けない
- is_top3 ヘッドのラベルは**頭数に関係なく `finish_position <= 3`**（`train_chihou_market_lgb.py:550`）。
  正規化するなら「3着以内率」として合計3に揃える。5〜7頭立ての「複勝圏（2着以内）」へ合計2で押し込むと意味が壊れる

### 1.3 組合せ確率の既存資産は本番から切り離されている

`backend/src/betting/` 配下（`finish_order.py` の harville / henery / lgb 等）は、本番のどこからも import されていない。
保存されている Henery λ は v26 時代の確率に合わせた値で、今の較正済み確率に当てると悪化する。
