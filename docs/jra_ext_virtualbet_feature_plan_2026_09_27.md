対象: `https://d374d8pjjxnppk.cloudfront.net/`（`stats.html` / `index.html` / `history/` / `about.html`）
柱: `jra`（収集テーブルの Alembic は `shared` → 別 PR）
状態: **調査・検証 済 / 実装 未着手**。Phase 0（利用可否の確認）待ち。

## 0. 結論（先に）

1. **このサイトの確率は、中身がほぼ市場（単勝オッズ）そのもの。**
   発走5分前版は確定オッズと相関 **ρ=0.975**、朝版は前夜オッズと
   **レース内 ρ=0.958**。本システムの指数（v28）との相関は 0.69〜0.84 で、
   サイトの確率は「v28 とは別物・市場とはほぼ同一」（§3）。
2. **したがって総合指数（composite / reg_rank / 単勝・複勝ヘッド）の特徴量には入れない。**
   composite はオッズ非依存を前提に設計されており（tier の第一分岐 `market_agree` は
   「指数がオッズと独立に1位を選ぶ」ことに意味がある）、市場込みの値を入れると
   地方 v13 と同型の壊れ方をする（§4）。
3. **使える可能性があるのは「サイト確率 − 市場確率」の残差**と、**確率以外の出力
   （位置取り予想・ペース予想・決着時計予想）**。ただし、
4. 🔴 **過去データが無い。** 検証（過去1年）の履歴ページには各馬の確率が
   **1件も残っていない**（買い目と上位3頭だけ）。各馬の確率が見られるのは
   **2026-09-26 以降の実運用分だけ**。朝版は `index.html` 上にしか出ず上書きされる。
   → **こちらで撮って貯めるしかない。** 判定できるのは 1 四半期貯めた後（§6）。

**推奨する進め方**: Phase 0 で利用可否を確認 → 収集だけ先に始める →
2026Q4 を貯めて事前登録どおり一度だけ評価 → 合格したものだけ `place_ev` 等の
**市場込みレイヤ**に入れる。composite は触らない。

## 1. サイトの正体

- 個人運営の「独自モデルで仮想購入した成績を出すサイト」。**実際には買っていない**と明記。
  `<meta name="robots" content="noindex,nofollow,noarchive">`。S3 + CloudFront の静的配信
- データ源は **JRA-VAN**（`about.html`「7:00 JRA-VANから最新データを取り込み」）。
  → 本システムと**入力の出どころが同じ**。独自情報源による上積みは期待しにくい
- 買い方（複勝期待値 ≥1.0 の「本命」と A/B/A+B）と、過去1年の検証 ROI 107%
  （本人も「条件をたくさん試した中から選んだぶん少し甘い」と書いている）
- モデルは **9/25 に固定**した版で過去1年を後から判断し直している。
  モデル更新があれば値の性質が変わる（非定常。§7 リスク）

### 1.1 ページごとに取れるもの

| ページ | 各馬の値 | レースの値 | 時点 |
|---|---|---|---|
| `index.html`（今日） | 馬番・馬名・人気・位置予想（逃げ/先行/中団/後方）・**1着率・2着内率・3着内率**（整数%） | 決着時計予想・ペース予想（前後半3F）・前に行きそう/後ろから 各3頭・当日バイアス（5R以降） | **朝版（03:15 オッズ）** → 発走5分前に正式版へ差し替わる（§2 で実測） |
| `history/YYYYMMDD.html`（実運用・9/26〜） | 上記 ＋ 確定着順・実際の最初のコーナー順位 | 上記 ＋ 結果 | **発走5分前版のみ**（朝版は残らない） |

## 2. 更新タイミング

### 2.1 本人の説明（`about.html`）

| 時刻 | 処理 |

### 2.2 実測（2026-09-27 日曜・阪神/中山 24R）

09:07〜18:07 に `index.html` / `stats.html` / `history/index.html` /
`history/20260927.html` の `ETag` を1分おきに記録し、変化ごとに本文を保存した
（本文 110 版。取得失敗 33 回は一過性で翌分に回復）。

| 対象 | 実測 |
|---|---|
| 朝版 | `index.html` は **07:16 生成**・「**03:15 のオッズ**で仮に判断」。**8:00・9:00 の再判断は1度も出なかった**（朝版の時点表記は終日 03:15 のまま） |
| 07:16 → 11:46 | **4時間半まったく更新なし**。1R〜4R（発走 10:00〜11:35）の判断は **11:46〜11:47 に一括で出た**（発走後 +17〜+111 分） |
| 5R 以降の正式版 | 各レースの**発走 1〜2 分前**に反映（1分ポーリングで「発走5分前」比 +3〜+5 分。5R/6R/7R の一部は +7〜+16 分の遅れ）。`stats.html` と `history/index.html` も同時に再生成 |
| `history/20260927.html` | 最終R（16:30）後の **16:51 に初出**、**17:14 に確定**（以後 18:07 まで変化なし） |
| 検証期間の `history/*.html` | 9/26 10:01 JST で固定（再生成されない） |
| キャッシュ | `Cache-Control: max-age=60`。CloudFront 越しでも最大1分遅れ |

🔴 **遅れて出た判断は発走後に作られている可能性がある。** 当日の履歴ページの注記は
「発走5分前の時点」ではなく「**判断の時点**」になっており、1R〜4R の確率は
発走後（確定オッズ相当）の入力で作られた疑いがある。**正式版を使うときは、
発走前に公開されたレースだけに限る**（公開時刻はこちらで記録しないと分からない）。

### 2.3 本システムの時刻との関係

| 本システム | 時刻 | サイトの値で間に合うもの |
|---|---|---|
| 当日一括算出（`jra_calculate_trigger.sh`） | 07:30 | 朝版（07:16 生成）だけ |
| 馬体重到着で再算出 | 発走約1時間前 | 朝版だけ |
| hit_tier 前向き記録 | 発走10分前 | 朝版だけ（正式版は5分前） |
| 複勝ピック確定 | 発走10分前 | 朝版だけ |

→ **正式版は、本システムのどの判断にも間に合わない**（実測で公開は発走1〜2分前。
締切2分前とほぼ同時）。
実用上の候補は**朝版**になる。ところが朝版は `index.html` にしか出ず、
履歴には正式版しか残らないため、**朝版を使うなら毎朝こちらで保存するしかない**。

## 3. 検証（手元で測ったもの）

いずれも小標本で、**方向を見るための確認であって採否の判定ではない**。

### 3.1 9/26（実運用初日・発走5分前版・23R / 306頭）

突き合わせは (開催日, 場名, R, 馬番) で **306/306 全件一致**（未一致 0）。

| 指標 | サイト | v28 | 市場（確定単勝オッズ正規化） |
|---|---|---|---|
| 勝ち馬の多項対数損失（低いほど良い） | 1.812 | 1.975 | **1.788** |
| 複勝の対数損失 | **0.407** | 0.427 | — |
| 1位馬の勝率 | 39.1% | 34.8% | 39.1% |

順位相関（全馬プール）: サイト〜市場 **0.975** / サイト〜v28 0.839 / v28〜市場 0.833

→ **サイトの発走5分前版は市場とほぼ同じ順位**。勝ち馬予測では市場を上回っていない。

### 3.2 9/27 朝版（03:15 オッズ・23R / 294頭）

DB の前夜最終スナップショット（`odds_history` 9/26 23:05 JST）と比較。

| 順位相関 | 全馬プール | レース内平均 |
|---|---|---|
| サイト〜市場 | **0.969** | **0.958** |
| サイト〜v28 | 0.755 | 0.694 |
| 市場〜v28 | 0.740 | 0.684 |

→ **朝版も市場とほぼ同じ**。「オッズを見ずに出した独自評価」ではない。
v28 と市場の関係（0.684）と、サイトと v28 の関係（0.694）がほぼ同じ＝
サイトは v28 から見て「市場と同じ場所」にいる。

### 3.3 位置取り予想（9/26・306頭）

| 予想 | 頭数 | 1着 | 3着内 |
|---|---|---|---|
| 逃げ | 23 | 3 (13%) | 10 (43%) |
| 先行 | 74 | 8 (11%) | 24 (32%) |
| 中団 | 111 | 8 (7%) | 20 (18%) |
| 後方 | 98 | 4 (4%) | 15 (15%) |

前ほど好成績だが、これは本システムも `past_form.runner_type_ord`（脚質）で既に持っている。
上積みがあるかは同条件比較が要る（§5 H2）。本人の検証値は
「1番手予想が実際に最初のコーナー1〜2番手: 53%」。

### 3.4 netkeiba マスターコース由来のデータは取れるか

サイトはマスターコース限定のデータも入力に使っているとのこと（ユーザー情報）。
ただし**公開4種のページ（今日・履歴・成績・仕組み）のどこにも生データは出ていない**。
出ているのはモデルの出力（確率・位置・時計・ペース）と JRA-VAN 由来の結果だけ。
→ **このサイト経由でマスターコースのデータそのものを取り込むことはできない。**
入っているとしても確率の中に溶けており、その正味の価値は H1（残差）で測る分に含まれる。

仮に生データが公開されていたとしても、第三者が転載した有料コンテンツを取り込むのは
netkeiba の規約・著作権の面で避けるべき。**正規の経路は自前の契約**で、
取得の実装は既に用意済み（`docs/netkeiba_running_data_plan_2026_09_17.md`・
`src/scrapers/netkeiba/running_data_job.py`。契約待ち）。こちらは
**過去分（個別ラップ 2024〜・走行距離 2025〜）を遡って取れる**ので、
蓄積待ちが要る本サイトより検証が早い。

## 4. 総合指数の特徴量にしない理由

1. **composite はオッズ非依存が前提。** v27/v28 の特徴 34/38 列にオッズ・人気は無い。
   推奨 tier の第一分岐 `market_agree`（指数1位 = 単勝1番人気か）は、指数が市場と
   **独立に**選んだ1位が市場と一致するから意味がある。市場込みの値を入れると
   指数が市場に寄り、`market_agree` が自己一致になって tier の分離が壊れる
2. **地方 v13 の教訓**（CLAUDE.md）: 市場込みで学習し、配信時に市場が中立値になって
   指数1位の勝率が 6.6〜13.6pt 落ちた。今回も「学習は正式版、配信は朝版」になれば
   同じ型の train/serve skew になる
3. **過去データが無い**ので、四半期ローリング（`jra_protocol.py`）の学習に乗せるには
   最低でも数四半期の蓄積が要る。1四半期ではヘッドの再学習に足りない

## 5. 検証仮説（事前登録）

評価窓は **2026Q4（2026-10-01〜12-31・約860R 見込み）**。**一度だけ**評価し、
`record_test_usage()` で台帳に記録する。仮説・指標・合否線は**収集開始前に固定**する。

使う時点はすべて**朝版**（本システムの判断に間に合う唯一の版。§2.3）。
比較の市場は「朝版と同時刻に DB にある単勝オッズ」とし、発走前オッズとの差でも見る。

| # | 仮説 | 指標 | 合格線 |
|---|---|---|---|
| H1 | 残差 `logit(サイト3着内率) − logit(市場由来の3着内確率)` が、**v28 複勝確率＋発走10分前市場**に上積みする | 複勝の対数損失（レース単位 paired bootstrap） | 95%CI 上端 < 0 |
| H1' | 同上（勝ち馬） | 勝ち馬の多項対数損失 | 95%CI 上端 < 0 |
| H2 | 位置予想（逃げ/先行…）が `runner_type_ord` に上積みする | 最初のコーナー順位の予測誤差 ／ 3着内の対数損失 | 95%CI 上端 < 0 |
| H3 | 決着時計・ペース予想が、本システムの既存値に上積みする | 勝ち時計 MAE ／ ペース区分の的中率 | 本人値（0.8秒・55%）の再現と上積み |

- H1/H1' の「上積み」は、**v28 複勝確率と市場由来確率のロジスティック混合**（基準として新たに作る。本番に同じものは無い）を基準に、
  残差1列を足して VAL（Q4 開始前の蓄積分。**朝版は 9/27 の 23R しか無い**——9/26 の朝版は撮れておらず正式版だけが残る）で係数だけ決め、Q4 で一度だけ評価する
- **不合格なら採用しない。** 合格しても入れる先は `place_ev`（複勝の期待値）や
  複勝ピックなど**もともと市場を使っている層**に限る

## 6. 計画

### Phase 0 — 利用可否の確認（ユーザー判断・着手前に必須）

- サイトの運営者と、機械的に取得して自システムに保存してよいか。

  開催中に `index.html` 1本を数分おきに見る必要がある（1本・3分間隔で1日約150リクエスト）

### Phase 1 — 収集（2〜3日）

| 作業 | 柱 | 備考 |
|---|---|---|
| 収集テーブル新設（Alembic） | shared | **単独 PR で先に入れる**。rev-id は `YYYYMMDDHHMM_shared` |
| パーサ（純関数・HTML → 行） | jra | `backend/src/scrapers/` 配下。**HTML 構造が変わったら 0 行で黙らず失敗させる**（行数・列数・確率合計の検査） |

## 7. リスク

| リスク | 影響 | 対策 |
|---|---|---|
| 個人サイトが予告なく止まる・形式が変わる | 特徴量が消える | 中立値への退避。パーサは黙らず失敗 |
| サイト側のモデル更新 | 値の性質が変わる（非定常） | 世代を記録し、評価は世代内で行う |
| 市場とほぼ同一 | 上積みが無い可能性が高い | H1 の合格線を厳しく置き、不合格なら撤退 |
| 整数%の丸め | 人気薄の情報が消える | 残差は 1% 以上の馬に限る案も VAL で確認 |
| 入力元が同じ JRA-VAN | 独自情報が乏しい | H2/H3（確率以外の出力）を並行して見る |
| 許可が得られない | 収集できない | Phase 0 で止める |

前提の確認（どちらかが崩れたら以下は無意味になるので先に見た）:

### 10.2 突き合わせ

履歴 16日・451R・6,109頭を (日付, 場名, R, 馬番) で `hit_tier_picks`（**kiseki が発走10分前に
実際に配信した値**）と突き合わせ: 445R・6,019頭が一致。確定・全馬にオッズと確率が揃う

look-ahead は無い。複勝圏は 8頭以上=3着内・7頭以下=2着内（サイトと同じ）。

⚠️ **時点がそろっていない。** サイトは発走2分前（馬体重・当日の前のレース・直前オッズ入り）、
kiseki と市場は発走10分前。**サイト側が有利な比較**で、朝版の「実」はこれより弱いはず。

### 10.5 次の手（推奨）

**後悔しない一手: 朝版と30分前版の全馬表を貯め始める。** 履歴に残るのは2分前版だけで、
kiseki の判断に間に合う版はこちらで撮らないと残らない（§2.3 と同じ）。
通知の runner（`mekauchida_runner.py`）は既に開催中 10分おきに `index.html` を取っているので、
**取得を増やさずに**全馬表（実・オッズ込み・位置予想）を保存できる。
新テーブルは shared の Alembic になるので単独 PR（#718 の後）。

確認（事前登録・**2026-11-21 以降に撮った朝版だけ**を使う）:

| # | 仮説 | 指標 | 合格線 |
|---|---|---|---|
| K1 | kiseki＋実（上の固定係数）が kiseki に勝つ | 複勝圏 / 勝ち馬の対数損失 | 両方 95%CI 上端 < 0 |
| K2 | 市場＋kiseki＋実 が 市場＋kiseki に勝つ（`place_ev` 用） | 複勝圏の対数損失 | 95%CI 上端 < 0 |
| K3 | サイトの買い目の前向き回収率 | 単3＋複7 / 複勝 | 記録のみ（判定しない） |

- 評価は**約300R 貯まった時点で一度だけ**（中央は1日約24〜36R・10日程度）
- 合格したら入れる先: 確率の層（`win_probability` / `place_probability` を上の結合で作り直す）。
  `composite_index`（LightGBM）の学習には入れない（2か月分しか無い）。
  **サイトが止まったら kiseki 単独へ落ちる経路**を必ず付ける（§7）
- 「指数」に取り込むと、kiseki の推奨が個人サイト1つに依存する。止まった・モデルを変えた日に
  性質が変わるので、世代（サイトのモデル更新日）を毎行に記録する
