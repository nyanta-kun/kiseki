# 地方 足切り閾値が v14 のスケールに合っていない（2026-09-02 発見）

> 測定バグ（`ci.version = 13` の直書き）を直した結果として出てきた。
> **バグが本物の不具合を隠していた**という関係にある。

## 何が起きているか

足切りルール `gap >= 30 または (gap >= 24 かつ 指数順位 >= 7)` は **v13 の
composite スケールで較正した値**（除外率 31%・除外馬の着外率 92.5〜93.6%・
1着取りこぼし 3.9〜2.9% を狙って選んだ）。

v14（2026-08-14 デプロイ・市場特徴5本を削除）は composite のレース内 gap が
縮んでおり、**同じ閾値が設計の半分以下しか効いていない**。

### 同一レースでの直接比較（2026-08-01〜08-13・約450R）

| 版 | 除外率 | 除外馬の着外率 | 1着取りこぼし | 3着内取りこぼし |
|---|---|---|---|---|
| v13 | **29.8%** | 92.8% | 3.3% | 6.8% |
| v14 | **13.8%** | 93.5% | 0.9% | 2.9% |

### gap 分布（2026-07-01 以降）

| 版 | p50 | p75 | p90 |
|---|---|---|---|
| v13 | 20.6 | 26.2 | 29.4 |
| v14 | **14.9** | **21.5** | **26.2** |

`gap >= 30` は v14 では p90（26.2）より外側にあり、ほとんど発火しない。

## なぜ気づけなかったか

`chihou_cutoff_venue_review.load_db` の SQL が `ci.version = 13` を直書きしており、
v14 デプロイ後もこの検証は **v13 の行だけ**を読んでいた。そのため月次レポートは
「除外率 27.7%」と設計どおりの数字を出し続けていた。**版の指定漏れは例外に
ならず、古い行を静かに読むだけ**なので、レポートの見た目からは分からない。

検査: `backend/tests/test_chihou_index_version_not_pinned.py`
（`calculated_indices` を読む SQL に version の直書きが無いことを固定）

## 影響

- 画面のグレーアウトが設計より大幅に少ない（**14.5% しか足切りされていない**）
- 取りこぼしは**減っている**（1着 0.7% / 3着内 2.8%）ので危険な方向ではない。
  「効きすぎて良い馬を捨てている」のではなく「ほとんど何も捨てていない」
- 誤って記録された 202608 の月次評価は台帳で無効化済み

## 再較正の材料（v14・2026-07-01〜08-31・2,310R・**in-sample**）

| hard | soft | 順位 | 除外率 | 着外率 | 1着落ち | 3着内落ち |
|---|---|---|---|---|---|---|
| 30 | 24 | 7 | 14.1% | 94.3% | 0.7% | 2.7% |
| **24** | **18** | **7** | **30.6%** | **91.0%** | **3.9%** | **9.2%** |
| 20 | 15 | 7 | 41.0% | 88.8% | 7.7% | 15.3% |
| 18 | 14 | 7 | 45.6% | 87.5% | 10.4% | 19.1% |
| 16 | 12 | 7 | 51.7% | 86.0% | 13.8% | 24.2% |
| 15 | 11 | 7 | 54.7% | 85.1% | 15.8% | 27.2% |

参考: v13 の運用点は 除外率 29.8% / 着外率 92.8% / 1着落ち 3.3%。

→ **除外率で揃えるなら `24 / 18 / 7`。** ただし同じ除外率で比べると v14 の方が
着外率が低く（91.0% vs 92.8%）、1着落ちも多い（3.9% vs 3.3%）。
市場特徴を外した v14 は「捨ててよい馬を見分ける力」自体が v13 より弱い可能性がある。

## 🔴 この文書では閾値を変更していない

理由:

1. **上の表は in-sample**。元の 30/24/7 は honest 手順（train ≤ TRAIN_END /
   test 2026-01〜06）で較正した値であり、置き換えるなら同じ手順を踏むべき
   （`chihou_cutoff_venue_review.py --source honest`）
2. 除外率を 14% → 31% にするのは**画面の見え方が変わる商品判断**。
   グレーアウトされる馬が倍以上になる
3. v14 は同一除外率での質が v13 より低いので、「v13 の運用点へ戻す」ことが
   正解とは限らない。**除外率を揃えるのか、着外率を揃えるのか**を先に決める必要がある

## 次にやること

1. `--source honest` で同じスイープを回し、in-sample でない表を作る
2. 揃える軸（除外率 / 着外率 / 1着取りこぼしの上限）をユーザーと決める
3. 決めたら `frontend/src/components/ChihouRaceDetailClient.tsx` の
   `CUT_GAP_HARD` / `CUT_GAP_SOFT` / `CUT_RANK_MIN` と
   `backend/scripts/chihou_cutoff_venue_review.py` の同名定数を**同時に**直す
   （後者のコメントに「frontend と一致させること」とある。正本が backend に無い
   のは既知の弱点）
4. 凡例テキストも同時に直す（現在は 20/15/5位 と書かれており実装 30/24/7 と食い違っている）

# 決着（2026-09-06）— 28/22/7 を採用

上の「次にやること」1〜3 を実施した。**本文（〜2026-09-02 部分）は書き換えていない。**

## 軸の決定: 1着取りこぼしの上限

ユーザー判断で **「1着取りこぼし <= 3% を制約に、その下で除外率を最大化」** に決めた。
却下した2案の理由:

- **除外率を揃える**: 同じ除外率で v14 の質は v13 より低い。「見た目を保つ代わりに
  劣化を黙って輸入する」ことになる。実際 v13 の運用点 24/18/7 を v14 に当てると
  1着取りこぼしが **5.3〜5.5%**（v13 は 3.3%）まで悪化する
- **着外率を揃える**: 切る量を減らすほど良くなる量なので、単独の目標にすると
  「何も切らない」が最適解になり目標として成立しない

## 🔴 較正の前に直した2つの不一致（どちらも「本番に無いモデルへ較正する」型）

1. **`--source honest` が v13 を再現していた。** `build_honest` が `ALL_FEATURES`（44・
   市場込み）で学習していたが本番 v14 は `PROD_FEATURES`（39）。さらに `train_binary`
   （early stopping・5seed 平均）で、本番の `train_binary_control`（固定 round・seed 0・
   単一モデル）と別レシピだった。**どちらも composite の散らばりを変える**ので、
   gap という絶対量の較正では直接バイアスになる。`ci.version = 13` 直書きと同型
2. **ルールが4箇所に重複していた。** 正本を `src/indices/chihou_cutoff.py` に作り、
   frontend は API の `is_cut_off` を受け取るだけにした（JRA の `out_probability` と同じ形）。
   `chihou_cutoff_venue_review.py` / `chihou_cutoff_review.py` も正本を呼ぶ

## 手順: walk-forward（単一 vintage の honest ではなく）

本番は毎月「先月末まで学習 → 当月を採点」を繰り返す。単一 vintage（train ≤ TRAIN_END）
で較正すると**本番より 1 年ぶん学習の少ないモデル**に閾値を合わせることになる。
そこで評価月ごとに前月末までで学習し直した（`scripts/chihou_cutoff_recalibrate.py`）。
学習レシピは本番と同一、**学習窓だけ**を月次で動かす。

VAL 2025-07〜2026-08（14か月・15,668R）を W1(202507-202601) / W2(202602-202608) に割り、
**両窓で制約を満たす**ものだけを候補にした（1窓だけだと good period に乗った候補が通る）。

## 結果（除外率・着外率・1着落ち・3着内落ち は W1 / W2）

| hard/soft/順位 | 除外率 | 着外率 | 1着落ち | 3着内落ち |
|---|---|---|---|---|
| 30/24/7（旧） | 19.4 / 17.7% | 93.0 / 93.0% | 1.7 / 1.7% | 4.6 / 4.2% |
| **28/22/7（採用）** | **25.1 / 23.3%** | **92.4 / 92.0%** | **2.6 / 2.7%** | **6.6 / 6.3%** |
| 26/22/7 | 26.2 / 24.4% | 91.8 / 91.6% | 2.8 / 3.0% | 7.3 / 7.0% |
| 24/18/7（v13 運用点） | 37.1 / 35.0% | 90.5 / 90.0% | 5.3 / 5.5% | 12.0 / 11.9% |

制約を満たす候補は 114 通り中 24 通り。**除外率が最大なのは 26/22/7 だが採らなかった**
——W2 の1着取りこぼしが 3.0% と制約の境界にあり、W1 の 95%CI 上端が 3.2% で余裕が無い。
除外率の差は 1.1pt しかないので、余裕のある側を採る。

**28/22/7 は v13 の質のプロファイル（着外93.6 / 1着落ち2.9 / 3着内落ち6.9）を
ほぼ再現し、除外率だけが 31% → 25% になる。** 同じ除外率まで切ろうとすると
1着取りこぼしが倍になるので、「v13 と同じだけ切る」は v14 では選べない。

🔴 **hard はこの範囲でほとんど効いていない。** gap の p95 が 28.8〜30.3 なので
30 以上はまず発火せず、28/24/5・30/24/5・32/24/5 は数字が完全に一致する。
効いているのは soft 24→22 の側。

## 転移チェック: walk-forward のスケールは本番と一致する

2026-07〜08（本文の DB 実測と同じ窓）の gap 分位:

| | p50 | p75 | p90 |
|---|---|---|---|
| walk-forward | 14.8 | 21.4 | 26.1 |
| 本文の DB 実測（v14・in-sample） | 14.9 | 21.5 | 26.2 |

**スケールは一致する**ので閾値はそのまま本番に載る。一方 **取りこぼし側は in-sample が
楽観に出る**（24/18/7 の1着落ち: 本文の in-sample 表 3.9% → walk-forward 4.3%）。
本文 §「再較正の材料」の表を採否判断に使わなくて正解だった。

⚠️ **除外率は時期でかなり動く。** 同じ 30/24/7 が W1 19.4% / W2 17.7% /
2026-07〜08 だけなら 13.7%。「除外率 x% を維持する」という目標が
そもそも安定しないことも、軸に除外率を採らなかった理由を裏づける。

## 商品面の影響

グレーアウトされる馬が **約14% → 約25%** に増える（2026-07〜08 の実測では 13.7% → 18.9%）。
1着馬をグレーにしてしまう率は 0.9% → 1.6%（同窓）。

TEST（`chihou_protocol.TEST_START` = 当月1日 = 20260901）は**消費していない**。

## 恒久対策（未着手）

gap は絶対量なので**版が変わるたびに壊れる**（v12→v13、v13→v14 と2回連続）。

`place_probability` は DB・API・frontend の型まで既に通っている。
移行の前に `place_probability` の較正（ECE）を測ること。
